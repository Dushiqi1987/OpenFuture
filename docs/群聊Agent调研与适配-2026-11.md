# 群聊式多 Agent：开源方案调研与 OpenFuture 适配（2026-11）

> 目标：让 2–3 个 Agent 在同一"群"里**串行**发言，主 Agent 先做事并把结果贴进群，评审 Agent 基于任务目标与证据提出质疑，双方商讨到收敛，最终给出双方都认可的方案。
>
> 本文先回答"别人怎么做"，再回答"六个具体设计问题"，最后给出本仓库的落地设计。

## 1. 结论 TL;DR

1. **"群聊"不是把多个 Agent 塞进一段对话历史，而是"共享转写稿 + 各自独立上下文 + 一个调度者"**。AutoGen/AG2 的 `GroupChat` 是这一形态的经典实现：群聊管理器持有全局消息序列，每个参与者用自己的上下文缓冲，调度者决定下一个发言者。
2. **最火/最稳的项目**（2026-11-12 GitHub 数据）：MetaGPT 71.3k★、crewAI 60.8k★、LangGraph 44.8k★、AgentScope 35.8k★、ChatDev 34.7k★、OpenAI Agents SDK 30.6k★、llm-council 26.4k★。**但 AutoGen 已归档**（README 明示 archived，后继是 Microsoft Agent Framework），选型时不能只看 star 数。
3. **对"评审-收敛"最有参考价值的三份实现**：
   - AutoGen `SelectorGroupChat`：LLM 选下一位发言者 + 每 Agent 独立 `model_context`（`BufferedChatCompletionContext` 按条数裁剪）；
   - ChatDev：**阶段化**（Phase）+ 用 `<INFO>` 标记从对话中抽取"研讨结论"，抽不到就 `self_reflection` 重试；
   - llm-council：**匿名评审**（Response A/B/C）+ 严格排名格式 + 主席综合，直接压制"看人下菜"和身份偏见。
4. **Cognition《Don't Build Multi-Agents》与 Anthropic 多 Agent 研究系统**给出了反面与正面经验：前者主张"共享完整上下文、动作隐含决策，单线程更稳"；后者用 orchestrator-worker 拿到 +90.2% 的效果但消耗约 15× token。结论：**群聊适合高价值、可验证的任务，且必须显式控制上下文与轮次**。
5. **本仓库落地**：新增 `GroupChatRuntime`（串行圆桌：主研 → 评审 → 回应 → … → 共识），复用现有 in-process 子会话能力；只读工具给双方、执行权归主研；共识以 `【共识】` 标记抽取，抽不到就判定"未收敛"并把分歧交还用户。

## 2. 群聊形态的四类实现

| 形态 | 代表 | 调度方式 | 上下文 | 适合 |
| --- | --- | --- | --- | --- |
| 群聊管理器（GroupChat） | AutoGen/AG2 `GroupChat`、`SelectorGroupChat`、MAF group collaboration | LLM 选人 / 轮转 / 手动 | 每 Agent 独立 buffer，调度者持有全局历史 | 开放讨论、角色扮演 |
| 阶段流水线（Phase/Chain） | ChatDev、MetaGPT SOP | 固定阶段与角色对 | 每阶段独立会话，结论落"环境" | 可拆解的工程流程 |
| 广播中心（MsgHub） | AgentScope `msghub` | 参与者按顺序响应，消息广播进各自 memory | 各自 memory + 广播 | 多角色协作、仿真 |
| 独立作答 + 互评（Council/Debate） | llm-council、multiagent-debate | 先并行独立作答，再匿名互评，最后主席综合 | 每次调用独立上下文 | 提高正确性、抗偏见 |

## 4. 六个关键设计问题

### 4.1 工作区怎么选

- **AutoGen/AG2**：群聊本身不管理文件系统，工具由各 Agent 自带；同一进程里共享 cwd 是常见做法，写冲突靠"谁在发言"隐式串行化。
- **ChatDev**：`ChatEnv` 是**共享环境**（`workspace/` 目录 + 人员表 + 配置），每个 Phase 只把"结论"写回环境，下一个 Phase 读环境而不是读上一个人的完整对话。
- **MetaGPT**：`Environment` 是消息池 + 共享文件仓库，角色通过 `publish_message/observe` 交换产物。
- **本项目**：**共享同一 workspace（同一 cwd），不做 worktree 复制**。理由：群聊是"同一件事的讨论"，不是并行开发；复制工作区会让"证据"分叉。若未来开放写工具，约定**只有主研有写权限**，评审只读，并在每轮结束生成 `git status/diff` 摘要进证据台账。

### 4.2 提示词怎么拼接：是拼接群聊记录吗

- **AutoGen 0.4**：每个参与者收到的不是"一整段拼接 prompt"，而是按消息逐条注入自己的 `model_context`；调度者另有一份 `history` 文本（`construct_message_history` 用 `\n\n` 连接）用于选人。
- **AutoGen 0.2/AG2**：`GroupChat.messages` 是全局列表，`_oai_messages[agent]` 是按 Agent 保存的消息视图；"auto" 选人时把 `select_speaker_message_template`（含 roles）放在最前，`select_speaker_prompt_template` 放在最后。
- **ChatDev**：每次 Phase 新建 `RolePlaying` 会话，system prompt = 角色提示 + 阶段提示（含占位符渲染），**不携带上一阶段全文**，只携带"结论"。
- **本项目**：三层拼装，**不做全量拼接**：
  1. `system` = 角色卡 + 群规 + 输出契约（稳定，便于命中缓存）；
  2. 每轮 `user` = 任务简报 + 共识台账 + **上一轮以来的转写增量**（`[#seq 说话人] 内容`）+ 本轮指令；
  3. 历史过长时，把更早的转写压成"阶段纪要"（保留结论、证据编号、未决问题），而不是重发原文。

### 4.3 身份提示词怎么拼接

- **ChatDev**：`RoleConfig.json` 里每个角色有 `role_prompt`（"你是某某公司的 CTO…"），阶段提示再叠加 `{chatdev_requirements}` 等占位符。
- **CAMEL**：`assistant_role_prompt` / `user_role_prompt` + `task_prompt`，system 里明确"你是 <role>，你的任务是 <task>"。
- **llm-council**：没有持久身份，靠"匿名标签 + 明确评分指令"避免身份影响判断。
- **本项目**：角色卡固定四段——**身份**（你是谁、代表什么立场）、**职责**（本轮必须产出什么）、**权限**（能用哪些工具、能不能写）、**判据**（什么算好、什么必须反对）。身份不写进群聊记录，避免被后续消息污染；评审角色额外要求"每条质疑必须给证据或验证方法"。

### 4.4 上下文怎么压缩

- **AutoGen**：`BufferedChatCompletionContext(buffer_size=N)` 只保留最近 N 条；`TokenLimitedChatCompletionContext` 按 token 截断；`initial_messages` 保住 system。
- **ChatDev**：**不压缩**——每阶段重开，只传结论，压缩问题被结构消解。
- **MetaGPT**：`role.rc.memory` 按 `watch` 过滤只取相关消息，属于"选择性记忆"。
- **本项目**：三层压缩：① 增量注入（只发新消息）；② 台账常驻（任务简报 / 已确认结论 / 证据编号 / 未决问题）；③ 超预算时把旧转写摘要为阶段纪要。预算：每轮输入 ≤ 12K 字符（转写 8K + 台账 2K + 其余 2K），超限先摘要再截断，并在台账里记录"已压缩到第 N 轮"。

### 4.5 工具调用怎么进行，会不会冲突

- **AutoGen/AG2**：工具是 Agent 自己的，群聊不协调工具；并发只发生在并行 Team（`RoundRobinGroupChat` 仍是轮转，工具调用在单个发言者内）。
- **ChatDev**：Phase 内由"助手"执行代码/写文件，环境串行更新，天然无并发写。
- **本项目**：**串行发言保证同一时刻只有一个 Agent 调工具**；工具结果以"证据条目"（E1、E2…）写进台账，后续发言者看到的是摘要而非原始大输出；评审工具白名单只读 + 每轮调用上限 + 相同 `(tool,args)` 结果去重；工具失败必须在发言里显式标注，禁止静默重试。

### 4.6 冲突与"被带偏"

| 机制 | 出处 | 本仓库做法 |
| --- | --- | --- |
| 匿名评审 | llm-council | 评分/排序时用"方案 A/B"匿名，身份映射只在最终汇总时还原 |
| 强制证据 | Magentic-One 台账、Anthropic 子任务描述 | 每条主张标注 E 编号或"假设"；无证据不能作为共识依据 |
| 非对称权限 | ChatDev 角色分工 | 主研可执行、评审只读；评审不能接管执行 |
| 防谄媚 | 辩论类实现 | 评审每轮必须给 ≥1 条新风险或明示"无新增风险"；主研必须逐条回应，禁止一句"同意"收尾 |
| 停滞检测 | Magentic-One `progress ledger`（is_in_loop / is_progress_being_made） | 连续两轮无新证据且无工具调用 → 判停滞，直接输出未收敛 |
| 主席不创作 | llm-council Stage 3 | 汇总只能综合已有内容；新增主张必须标注来源，否则丢弃 |
| 显式未收敛 | ChatDev `<INFO>` 缺失则反思 | 抽不到 `【共识】` 或双方立场不一致 → 输出 `【未收敛】` + 分歧清单，交还用户 |

## 5. 本仓库的群聊协议

### 5.1 角色（默认两个，可选第三个）

| 角色 | 职责 | 工具 |
| --- | --- | --- |
| 主研（lead） | 拆解任务、执行调查/实验、贴出工作汇报、回应质疑、修订方案 | 与主 Agent 相同的只读工具 + web/time（未来可含写工具） |
| 评审（critic） | 基于目标与证据挑错、给可验证的反对意见、表态 | 只读工具子集，每轮上限 6 次 |
| 主持（chair，可选） | 只在最后出场，按台账与转写生成共识，不引入新主张 | 无工具 |

### 5.2 消息与标记

```text
[#1 主研/工作汇报]
目标复述：…
做了什么：…（证据 E1, E2）
结论：…
不确定点：…

[#2 评审/质疑]
逐条质疑：
1. …（依据 E1 / 需验证：…）
2. …
立场：反对 | 存疑 | 同意
阻断项：有/无

[#3 主研/回应]
回应 1：接受 → 修订 …
回应 2：反驳 → 依据 E3 …
修订方案：…
立场：同意 | 存疑

[#4 主持/共识]  （或最后一轮由主研输出）
【共识】方案：… / 依据：E… / 未解决分歧：… / 风险：… / 下一步：…
```

### 5.3 收敛算法（确定性，不额外花 LLM 调用）

1. 至少跑满 `minRounds`（默认 1 轮"工作+质疑+回应"）。
2. 当评审 `立场=同意` 且 `阻断项=无`，且主研最后一条 `立场=同意` → 收敛，主持人输出共识。
3. 达到 `maxRounds`（默认 3）仍未满足 → 判未收敛，仍由主持输出"分歧清单 + 各自最优方案"。
4. 停滞检测：相邻两轮评审质疑文本相似度 > 0.9 且本轮无工具调用 → 提前终止，标记 `stalled`。

### 5.4 事件与 UI

新增 `group` 事件流（`group-start` / `group-message` / `group-end`），渲染层在输入框上方显示"群聊"面板：发言者、阶段徽标（工作/质疑/回应/共识）、轮次、状态。共识正文作为普通助手消息回给用户。

### 6.2 实测结果（2026-11-12）

- 离线冒烟 `node tools/group-chat-smoke.mjs`：共识路径 5 条消息（work → critique → response → critique → chair）、`status=consensus`、约 3.3s；未收敛路径（`rounds=1` + 阻断项）`status=unresolved`、3 条消息；两次共 6 个角色会话文件，全部带 `parentSession`。
- 桌面 E2E `pnpm build && node tools/e2e-group-chat.mjs`：真实 Electron + mock 模型，主 Agent 调用 `start_group_chat`，渲染层面板渲染出 5 条发言与「已达成共识 · 2/2 轮」，90 个事件、无 error；截图见 `docs/assets/group-chat-e2e.png`。
- 设计修正：角色会话在每次群聊结束时释放（`GroupChatRuntime.endChat()`），下一次群聊从干净上下文开始；会话文件仍保留在 `<sessionDir>/group/*.jsonl` 供审计。

### 6.3 手动入口（2026-11-12 补充）

群聊原先只作为工具暴露，模型不调用时用户看不到任何入口。补充一条与模型无关的路径：

- composer 工具栏「群聊」胶囊按钮 → 弹窗填目标（可带入当前草稿）与轮数 → `openfuture:group-chat:start` → `host.startGroupChat`，与工具调用共用同一个 `GroupChatRuntime` 和 `group` 事件流；
- 手动入口会先 `openConversation` 确保主会话存在（`startGroupChat` 需要 `sessionId`，渲染层也按它过滤事件），因此不需要先发一条消息"热机"；
- 面板只能由 host 的 `start` 事件创建：早期版本在 RPC 返回后先塞一个 `chatId:'pending'` 的占位，宿主的 `start` 可能更早到达而被覆盖，后续 `message`/`end` 因 `chatId` 不匹配被丢弃，面板会停在「讨论中 · 0/2 轮」；已改为纯事件驱动；
- E2E `E2E_GROUP_MANUAL=1 node tools/e2e-group-chat.mjs` 通过（7 个 group 事件、共识路径、面板完整渲染），截图 `docs/assets/group-chat-manual-e2e.png`。

### 6.4 侧边栏与成员模型（2026-11-12 补充）

需求（m01681）：群聊进入左侧栏，点开可看历史群聊，并能给每个成员指定模型（千问 / DeepSeek / GLM 混用）。

实现：

- **额外模型档案**：`settings.json` 增加 `groupModelProfiles[]`（label/baseUrl/modelId/contextWindow/maxTokens）与 `groupChatModels`（lead/critic/chair → 档案 id 或 null）。每个档案是一个独立 provider（`openfuture-g-<id>`），`writeModelsJson()` 把主模型和所有档案一起写进 `models.json`；密钥单独存 `config/secrets/group-<id>.bin`（safeStorage），主模型的单凭据路径不变。
- **角色 → 模型**：`groupChatStart` 时主进程把绑定换算成 `{providerId, modelId}` 一并下发给宿主的 `startGroupChat`，宿主用 `modelRuntime.getModel()` 解析后 `GroupChatRuntime.setRoleModels()`；没有绑定的角色回退主模型。因此换成员模型不需要重启进程，只有增删档案（改 `models.json`）需要。
- **凭据**：`setCredential` 原先只接受主 provider；现在接受 `models.json` 里注册过的任意 provider，`groupChatStart` 会先推主 key，再逐个推被绑定档案的 key，避免冷启动 401。
- **历史**：主进程 `GroupChatStore` 监听 `group` 事件，把 `start/message/end` 折叠成 `<userData>/config/group-chats/<chatId>.json`（含成员快照），面板通过 `listGroupChats`/`getGroupChat` 读取；渲染层不再是唯一存储。
- **UI**：侧边栏「群聊」→ `.group-chats-modal`，左侧历史列表（状态/条数/时间），右侧成员与模型下拉、额外模型增删改、完整讨论记录（含 `#seq`、阶段徽标、工具次数）。
- **验证**：`node tools/e2e-group-panel.mjs` 通过（新增档案 → 绑定评审 → 从 pill 开聊 → 共识 → 历史 5 条且成员快照正确；宿主日志 `critic=profile`），截图 `docs/assets/group-chat-panel.png`、`docs/assets/group-chat-panel-run.png`。

## 7. 参数与风险

| 参数 | 默认 | 上限 | 说明 |
| --- | --- | --- | --- |
| 角色数 | 2 | 3 | 第三个是主持，不参与讨论 |
| 轮次 | 2 | 3 | 一轮 = 工作/质疑/回应 |
| 单条发言 | 4000 字符 | 8000 | 超出截断并记入台账 |
| 扩展论输入 | 12000 字符 | — | 超限先摘要 |
| 评审工具调用/轮 | 6 | 10 | 只读白名单 |

风险：
- **token 成本**：一轮群聊 ≈ 3–4 次完整推理；Anthropic 数据表明多 Agent 约 15× 聊天成本，需在 UI 明示。
- **同模型互评**：同一模型扮演两个角色时容易"互相客气"，故用"强制证据 + 非对称权限 + 显式立场"约束；必要时可给评审换模型（P1）。
- **共识幻觉**：主持只能综合已有内容，新增主张需标注来源，否则丢弃并记入"未收敛"。
