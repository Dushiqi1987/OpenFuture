# BEIR / TREC-COVID 真实语料检索评测（2026-11-16）

## 1. 目的与口径

用真实医学文献替换合成语料，回答同一个问题：**OpenFuture 的记忆检索在真实文档上到底好用吗**。

- 数据：BEIR `trec-covid`（2020 年 COVID-19 文献，真实标题/摘要 + 人工相关性标注）。
- 全量语料 171,332 篇、50 条查询、qrels 66,336 行（17,537 篇被判为相关）。完整的 171k 篇无法通过「一文件一资料」的导入通道灌入（100 文件/批、2 MB/文件），因此评测使用**可复现切片**：
  - 取 15 条最小查询（相关文档 111–353 篇/条，平均 232）；
  - 切片包含这 15 条查询的**全部**相关文档（3,323 篇），再用固定种子 `20261116` 的 PRNG 补 4,677 篇随机干扰文档，合计 **8,000 篇**。
- 指标在切片内计算。切片含完整正例、但负例仅来自 4.7k 干扰项，**数字会高于全量 BEIR**；可横向比较三种检索配置，不可直接与官方榜单对比。
- 所有文档以 `<corpus-id>.md` 一文件一篇导入，标题就是文件 id（`title` 字段不含语义），所以这是**纯正文检索**，比真实网页场景更吃亏。

## 2. 方法

`tools/beir-trec-covid.mjs`：

1. 读取 `corpus.jsonl` / `queries.jsonl` / `qrels/test.tsv`，生成切片与 `trec-covid-subset.json`；
2. 以隔离 profile 启动真实 Electron，`memorySetMode('rag')`；
3. 每批 100 个文件调用 `memoryImportFiles({ paths })`（与界面「导入文件夹」同一链路）；
4. 逐条查询调用 `memorySearch({ query, limit: 100 })`，把命中的来源文件名还原成 corpus id；
5. 计算 nDCG@10（分级增益 1/2）、Recall@10、Recall@100、**Recall@100(cap)=命中数 / min(100, 相关数)**、MRR@10 与 p50/p95 延迟；
6. 通过 `OPENFUTURE_RETRIEVAL_MODE` 分别跑 `lexical` / `hybrid` / `hybrid-rerank`，复用同一份索引（不重复导入）。

## 4. 怎么读这些数字

- **首条命中率很高**：MRR@10 ≈ 0.89–0.90，15 条里 11 条的第一条结果就是相关文档。这符合「标识符/术语检索」强的特征（`HALCYON-001`、`COVID-19`、`remdesivir` 这类词面证据）。
- **nDCG@10 0.61–0.65，真实可用但不惊艳**：医学问题往往是宽泛的（「how does the coronavirus spread」），前 10 条里通常只有 1–2 条被判相关；判为相关的集合又很大（平均 232 篇），nDCG 对「少命中」非常敏感。
- **Recall@100 看着只有 0.15，是分母问题**：相关集 111–353 篇，只召回 100 条时理论上限就是 0.28–0.90；按可召回上限归一后是 **0.32**，即前 100 条里覆盖了三分之一的相关文献。
- **hybrid 与 lexical 完全相同**：救援式融合只在词法 0 命中时启用，而这里词法几乎总能凑满 100 条候选，所以没有触发；要验证混合收益需要用更小的 `limit` 或空结果查询。
- **rerank 在真实数据上反而掉了 3 个点 nDCG**（0.6457 → 0.6125），MRR 略升：合成语料上它是把 compare 从 50% 拉到 100% 的关键，但那是「同模板短文档 + 唯一代码」的分布。真实摘要更长、术语更密，启发式重排（锚点 + 三元组覆盖 + 最长公共子串）会牺牲覆盖换精度。**它不该是真实场景的默认值**，除非换成训练过的 cross-encoder。
- **性能明显劣化**：100 篇合成语料 8.7 ms，8,000 篇真实摘要 p50 194–279 ms。稠密通道每次查询要遍历全部证据向量（O(N)），这是主因；导入吞吐约 **14.5 篇/秒**（8,000 篇 552 秒）。

## 5. 结论

1. 链路在真实医学语料上**是通的、第一跳通常是相关的**，但「前 10 条里排进更多相关文献」和「召回更多相关文献」都明显弱于词面精确查询。
2. 现有「哈希向量 + 启发式 rerank」不足以支撑语义检索；rerank 默认值应回退到 `lexical`/`hybrid`，或仅在合成类语料启用。
3. 真正的提升点按性价比排序：
   - **换成训练过的 embedding**（bge-small / e5-small，本地 ONNX，几十 MB）替换哈希向量；
   - **cross-encoder rerank** 只对前 50 条重排（成本可控）；
   - **索引侧**：把 8k 证据的向量预计算并持久化，避免每次查询 O(N) 重建；
   - **分块**：医学摘要按章节/句子切分，当前 1,400 字符聚合对长摘要有损；
   - **查询侧**：把用户问题先抽关键词（术语/药物/编号）再检索，可显著提升宽泛医学问题的 nDCG。
4. 导入通道的限制（100 文件/批、2 MB/文件、14.5 篇/秒）决定了真实医学库需要**后台批量导入 + 进度**，当前实现只适合一次性小批量。

## 6. 复现

```bash
# 1) 下载并解压 BEIR TREC-COVID（约 70 MB）
curl -sSL -o .scratch/beir/trec-covid.zip \
  https://public.ukp.informatik.tu-darmstadt.de/thakur/BEIR/datasets/trec-covid.zip
# 解压到 .scratch/beir/trec-covid/（脚本期望 .../trec-covid/trec-covid/corpus.jsonl）

# 2) 生成切片 + 跑检索（默认 hybrid-rerank；mode 经环境变量）
node tools/beir-trec-covid.mjs
RETRIEVAL=lexical node tools/beir-trec-covid.mjs
RETRIEVAL=hybrid node tools/beir-trec-covid.mjs

# 报告：.scratch/beir/trec-covid-report-<mode>.json
```

调参：`QUERY_COUNT`（默认 15）、`POOL_SIZE`（默认 8,000）、`RETRIEVAL`。脚本会复用 `.scratch/beir-userdata` 里已导入的索引，不会重复灌数据。
