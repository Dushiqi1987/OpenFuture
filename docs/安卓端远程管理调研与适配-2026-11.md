# 安卓端远程管理调研与适配（2026-11）

> 目标：给 OpenFuture 做一个 Android APK，在外面用手机查看/接管电脑上的**项目**与**会话**（发消息、看流式输出、审批工具调用、停止任务）。
> 结论先说：**没有能直接装上就用的开源方案**。所有现成客户端都绑定自家运行时（DSH / Claude+Codex / opencode / herdr），对本项目只能「借壳、借协议、借 UI」，不能「装插件」。最省力的组合是 **自建远程宿主（HTTP+WS）+ 复用现有 React 代码的 Capacitor 壳**，约 15–24 人日可到可用 MVP。

- 调研日期：2026-11-16
- 调研方式：仓库源码 / Release / 官方文档直接核对（GitHub core API 当日限流，星数为 API 检索时的近似值）
- 现状基准：`D:\OpenFuture` 工作区，`PROTOCOL_VERSION = 1`

## 一、问题定义

「手机上管理电脑端项目和会话」拆成 6 个能力，按 MVP 优先级：

| 优先级 | 能力 | 说明 |
| --- | --- | --- |
| P0 | 项目列表 / 会话列表 / 历史消息 | 只读，验证链路 |
| P0 | 发消息 + 流式回显 | 真正的「远程会话」 |
| P0 | 审批（写工具 / 命令）与停止 | 否则手机端无法安全接管 |
| P1 | 文件预览、diff 卡片、任务状态 | 看结果，不改代码 |
| P2 | 记忆检索只读、群聊只读、插件/技能开关 | 管理面 |
| 不做（首版） | 手机上编辑代码、跑终端、装插件 | 输入体验与安全都不划算 |

**不做什么**同样重要：首版不做「移动端 IDE」，只做「远程遥控器 + 观察窗」。

## 二、OpenFuture 现状：可改造面与硬约束

### 2.1 进程与通信

- Electron 45 + React 19 + TS 7 + electron-vite；Agent 在 `src/agent-host` 的 utilityProcess 里跑 Pi SDK `@earendil-works/pi-coding-agent` 1.5.0。
- **纯 IPC**：`src/main`、`src/agent-host`、`src/preload` 中没有 `createServer` / `.listen(` / `WebSocketServer`。渲染层只通过 preload 暴露的 `IpcChannels`（`src/shared/protocol.ts`）拿 `IpcResult<T>` DTO。
- 含义：**手机端没有任何入口**。要远程，必须先造一个「服务端」，这是本项目最大的新增件。

### 2.2 数据模型（可直接映射到 API）

| 概念 | 落盘位置 | 备注 |
| --- | --- | --- |
| 项目 | `<userData>/config/projects.json`（`src/main/project-store.ts:124-125`） | `ProjectStore` + `FileStore`，整文件写 |
| 会话 | 同上 conversations 索引 + 磁盘 Pi 会话 | `ProjectConversation.piSessionId`（`src/main/project-store.ts:452-471`、`535-560`） |
| 群聊 | `config/group-chats/`（`group-chat-store.ts`） | 多 Agent 协作 |
| 自动化 | `config/automation.json` | 定时/触发 |
| 记忆 | memory-host 独占 SQLite | 跨进程不可直连 |
| 插件 | `plugins/` + `plugin-market.ts` | 目录 + manifest |

好处：`project-store` / `host-registry` 都已是「服务层」形态，**远程宿主只是多一个调用方**，不需要重构业务逻辑。

### 2.3 已有的远程桥原型（重要）

`parallel/multiagent/src/desktop/server.ts` 已经是一个可运行的 HTTP 桥：

- 默认 `127.0.0.1:19744`，`--token` 鉴权，`/v1/health`、`/v1/contract`、`/v1/...` 路由，`TeamError('desktop-not-found')` 统一错误。
- 入口 `parallel/multiagent/scripts/desktop-bridge.ts`，`test/m2-desktop.test.ts` 有 8 项合同测试。
- `docs/多Agent实现方案调研与适配-2026-11.md:42` 把它记为「原 HTTP 桥 + 任务图原型」。

它服务的是**任务图**而不是会话流，但**骨架（监听、鉴权、路由、错误码、测试写法）可以直接搬**，省掉一轮从零设计。

### 2.4 三条硬约束

1. **不能把 `App.tsx` 直接搬到手机**：它是桌面三栏布局（侧栏 + 会话 + 右侧面板），必须做移动版信息架构。
2. **不能直连 Pi 会话对象**：移动端只能消费 `src/agent-host` 已经推给渲染层的事件流（`AgentEvent`），协议设计要贴着这层做。
3. **`PROTOCOL_VERSION` 必须双向协商**：桌面升级后，旧 APK 不能静默错乱。

## 四、逐方案评估

### 4.1 ds-harness-remote —— 架构参考，不是壳

- `apps/server` 是自托管 Relay（单账号），`apps/android` 是 RN/Expo SDK 57 客户端，另有 Web 与 iOS beta；协议为 **Remote Protocol v1**。
- 传输顺序 **LAN → P2P → TURN → Relay** 自动降级，Host 只出站、不监听公网；E2E 用 `Noise_IK_25519_ChaChaPoly_SHA256`。
- 这解决了分布式部署里最难的三件事：**打洞、降级、端到端加密**。但它的协议围绕 DSH 的 host/session 模型，搬到 OpenFuture 等于重写服务端再加客户端改造。
- **可抄**：配对二维码 + 设备公钥、seq 断线补发、传输不可用时的用户提示文案。
- **可省**：首版不要 P2P/TURN，局域网 + 自建隧道足够。

### 4.2 happier —— 能力最全，体量也最大

- RN/Expo + Tauri 桌面 + Web + 自托管 relay（`happier relay host install --mode system`），E2E，Play/APK 都有。
- 支持 **Pi（ACP，实验）** 与 Custom ACP —— 这是唯一「理论上能接 Pi 但不接 OpenFuture」的点。OpenFuture 的 Pi 实例在 utilityProcess 内，对外没有 ACP 端点，接上去是另一个工程。
- 结论：**学它的多设备/relay 设计，不 fork**。

### 4.3 CC Pocket —— 功能最完整的移动端基座

- `apps/mobile` Flutter + `packages/bridge` Node/TS WS 桥（可直接 npm 装 `@ccpocket/bridge` 作为参考实现）。
- 已有能力几乎就是 P0 清单：`start` / `input` / `approve` / `list_sessions` / `get_history`，QR / mDNS / Tailscale 连接，Play + APK 分发。
- 协议是**公开文档化的 JSON WS**，README 还专门写了「Why Fork CC Pocket?」鼓励二次开发。
- 代价：Flutter/Dart 技能栈，且要重写它对接 Claude/Codex 的桥接尾部。**如果团队有人会 Dart，这是最快路径。**

### 4.4 ovis —— 参考「手机 Web UI」

- Bun + TS，xterm 前端，手机 App + 自有 relay，主打「在手机上盯着长跑的 Agent」。
- 它的**会话流 + 通知**交互值得抄；但底层是 herdr 的 pane/workspace 模型，与 OpenFuture 的项目/会话不同构。
- `@pierre/diffs` 做移动端 diff 渲染这条线索有用。

### 4.5 opencode-mobile —— 最薄的 TS 基座

- RN/Expo，请求走 opencode 的 HTTP + SSE（`opencode serve`），有 F-Droid / Play / APK，甚至带演示模式。
- 优点：**代码量小、易读、TS 栈与 OpenFuture 一致**，把 OpenFuture 伪装成 opencode 的 API 子集，改动集中在 adapter。
- 缺点：UI 很薄（会话列表 + 对话），审批/项目管理要自己补；opencode 的事件 schema 也得跟着模拟。

### 4.6 acp-ui —— 走标准协议的备选

- Vue 3 + Tauri 2 + `@agentclientprotocol/sdk ^0.13.1`，Web/桌面/Android 三端，远程 Agent 走 `ws://`/`wss://`，`$/ping` 心跳 25s。
- ACP 是「Agent ↔ 客户端」的标准协议，长期看最优：以后接别的 Agent 免适配。
- 但现在的问题是 **ACP 只覆盖会话，不覆盖项目/记忆/群聊**，且 OpenFuture 侧要先写 ACP 服务端（等于再做一套协议）。适合作为 **v2 的统一协议层**，不是首版。

### 4.7 明确排除

| 方案 | 原因 |
| --- | --- |
| claudecodeui（CloudCLI） | AGPL-3.0：闭源分发或 SaaS 化都要开源整个衍生作品 |
| coder/agentapi | 仓库已 deprecated |
| antigem | GPL-3.0 + Kotlin 原生 IDE，与本项目形态冲突 |
| anycoding | 老旧 Java 实现，无维护迹象 |

## 六、推荐方案设计

### 6.1 架构

```
┌────────────── Android (Capacitor WebView) ──────────────┐
│  React 移动端页面（项目/会话/对话/审批）                  │
│  transport 抽象：HttpTransport / ElectronIpcTransport     │
└───────────────▲──────────────────────┬───────────────────┘
                │ HTTPS / WSS          │ 设备 token + scopes
┌───────────────┴──────────────────────▼───────────────────┐
│ Electron 主进程：RemoteHost（新）                         │
│  ├─ 鉴权/配对/设备表（复用 DeviceStore）                  │
│  ├─ REST：projects / sessions / messages / files         │
│  ├─ WS：AgentEvent 广播（seq + 环形缓冲补发）             │
│  └─ 授权：把消息/审批投递给 host-registry 的会话          │
└───────────────▲──────────────────────────────────────────┘
                │ 既有 IPC
        project-store / host-registry / agent-host(Pi)
```

关键点：**RemoteHost 不直接碰 Pi 对象**，它通过 `host-registry` 拿会话句柄、订阅 `AgentEvent`，和渲染层平级。这样移动端与桌面端行为一致，也不会引入第二套状态机。

### 6.2 协议草案（贴着 `/v1` 骨架）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/v1/health` | 免鉴权，返回 `{version, protocol}` |
| POST | `/v1/pair/claim` | 一次性配对码 → `{deviceId, token}`（5 分钟过期，单次） |
| GET | `/v1/projects` | 项目列表（含 git 分支/最近会话时间） |
| GET | `/v1/projects/:id/sessions` | 会话列表（分页） |
| GET | `/v1/sessions/:id/messages?before=` | 历史（沿用桌面 DTO） |
| POST | `/v1/sessions/:id/messages` | `{clientId, text}`，幂等去重 |
| POST | `/v1/sessions/:id/stop` | 停止当前回合 |
| GET | `/v1/sessions/:id/approvals` | 待审批队列 |
| POST | `/v1/approvals/:id` | `{decision: allow/deny, scope: once/session}` |
| GET | `/v1/files?path=` | 只读、限定在项目根内 |
| WS | `/v1/events?since=seq` | 事件流；断线按 seq 补发 |

事件封套（与桌面 `AgentEvent` 一对一派生）：

```json
{ "v": 1, "seq": 1287, "type": "assistant.delta", "sessionId": "s_...", "ts": 1763260000000, "payload": { } }
```

- `seq` 单调递增，服务端保留最近 N 条（建议 2000）用于补发；超出则要求客户端全量刷新，避免「以为连续、其实漏了」。
- 心跳 25s（与 `acp-ui` 的 `$/ping` 同频），Android 前台服务期间保持。
- 版本不匹配：`426 Upgrade Required` + 提示升级 APK。

### 6.3 鉴权与「分用途授权」

这与 README 路线图的「远程设备分用途授权」对齐：

| scope | 允许的动作 |
| --- | --- |
| `read` | 项目/会话/消息/文件只读 |
| `chat` | 发消息、停止 |
| `approve` | 审批写工具与命令 |
| `files` | 文件下载（不含写） |
| `admin` | 设备管理、配对撤销 |

- 配对产物是**设备记录**：`{deviceId, 公钥, scopes, createdAt, lastSeenAt, revokedAt}`，存 `config/devices.json`。
- token 用设备密钥签名（Ed25519）而非长期 bearer 明文；吊销即时生效（每次请求查设备表）。
- 传输：局域网用自签证书 + 首次指纹固定（TOFU），或用隧道终结 TLS。
- 审计：每条远程指令写 `config/remote-audit.jsonl`（谁、何时、对哪个会话、做了什么），便于事后追溯。

### 6.4 移动端页面

| 页面 | 内容 | 复用 |
| --- | --- | --- |
| 配对 | 扫码 / 输入 `host:port` + 6 位码 | 新写（约 1 页） |
| 项目 | 卡片：名称、路径、分支、最近会话、运行中标记 | `project-store` DTO |
| 会话 | 列表 + 状态徽标（运行/等待审批/完成/失败） | `host-registry` 状态 |
| 对话 | 消息流、工具卡、diff 折叠、输入框、停止按钮 | `RichText.tsx` 渲染逻辑 |
| 审批 | 底部抽屉：命令/写入预览 + 允许一次/本会话/拒绝 | 新写（核心交互） |
| 设置 | 设备、权限、通知、退出配对 | 新写 |

**最重要的一条**：把渲染层的数据获取抽成 `useTransport()`（桌面 = IPC，移动 = HTTP/WS），组件才能两边共用。这一步现在做，成本远低于以后双份维护。

### 6.5 网络、后台与推送

| 问题 | 建议 |
| --- | --- |
| 局域网 | 首选。PC 监听 `0.0.0.0:19744`（仅私网），手机同 Wi-Fi 直连；二维码里带 IP 列表 |
| 外网 | 自建 WireGuard（如已有机房）或 frp；Tailscale 在国外好用，国内链路不稳，作为可选项 |
| 打洞/relay | 首版不做。等真有「不开 VPN 也要连」的需求，再抄 ds-harness-remote 的降级链 |
| 后台保活 | Android 前台服务（`FOREGROUND_SERVICE_DATA_SYNC`）+ 常驻通知 + 25s 心跳；厂商省电白名单引导 |
| 推送 | 国内优先 **ntfy 自建** 或 UnifiedPush；GMS 可用时接 FCM。国内机型无 GMS，FCM 不可靠 |
| 通知内容 | 只发「会话完成 / 等待审批 / 失败」，正文脱敏（锁屏可见性可关） |

### 6.6 安全清单

- [ ] 默认只监听回环，用户显式开启「允许局域网」才绑 `0.0.0.0`
- [ ] 配对码单次 + 5 分钟过期 + 限速（防爆破）
- [ ] 设备可单独吊销，吊销后立即断开 WS
- [ ] 文件接口规范化路径，拒绝 `..` 与项目根外路径
- [ ] 审批接口带 `approvalId` 与一次性 nonce，防重放
- [ ] 默认不给 `approve` scope（先只读 + 聊天），按需开
- [ ] 日志不落 token / 消息正文

| 阶段 | 交付 | 验收标准 | 人日 |
| --- | --- | --- | --- |
| M0 | RemoteHost 服务端（health/pair/projects/sessions/messages/WS）+ 合同测试 | `curl` 与 Node 客户端跑通配对→列表→发消息→收事件；断线 `since` 补发无误 | 4–6 |
| M1 | 移动端只读（项目/会话/历史/配对） | 真机同 Wi-Fi 打开即可浏览全部项目与会话 | 4–6 |
| M2 | 发消息 + 流式 + 审批 + 停止 | 手机发一条消息，桌面同步可见；审批后工具继续执行 | 4–6 |
| M3 | 后台保活 + 通知 + 断线重连 | 锁屏 10 分钟后任务完成仍能收到通知 | 2–4 |
| M4 | Capacitor 打包 + 签名 + 内测分发 | 生成可安装 APK，覆盖升级不丢配对 | 1–2 |

> 估算前提：熟悉本项目代码；不含 UI 视觉打磨与多端适配测试。PWA 先行的路线可把 M1 提前，M4 顺延。

## 八、风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 移动布局重做超预期 | 工期翻倍 | 先做 PWA 低保真，确认信息架构再美化 |
| 后台被系统杀 | 收不到完成通知 | 前台服务 + 厂商白名单引导 + 通知降级为「下次打开时补推」 |
| 海外隧道不可用 | 外网连不上 | 自建 WireGuard/frp 为主，Tailscale 备选 |
| APK 分发 | 上架成本/合规 | 首版 GitHub Releases 侧载，不上商店 |
| 双端协议漂移 | 旧客户端静默出错 | `PROTOCOL_VERSION` + `426` + 桌面端提示升级 |
| 安全面扩大 | 端口暴露被扫 | 默认回环、配对码限速、scope 最小化、审计日志 |

---

## 九、结论

1. **没有可直接适配的现成 APK**；`ds-harness-remote` 证明这类产品形态成立，但它绑死 DSH。
2. 若团队有 Flutter 能力，**Fork CC Pocket** 是功能最全的捷径；否则**自研 + Capacitor** 长期成本最低，且能复用现有 React/TS 资产。
3. 首版范围压在 P0 六件事（列表、历史、发消息、流式、审批、停止），不要做移动 IDE。
4. 协议从第一天就带 `seq`、`PROTOCOL_VERSION`、scope 与审计——这些是后面补不回来的。
