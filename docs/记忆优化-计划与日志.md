# 记忆架构优化：计划与日志

## 三种记忆架构（本轮目标）

| 模式 | 检索范围 | 入口 | 现状 |
| --- | --- | --- | --- |
| `rag` | evidence + note + wiki | 设置 → 记忆模式；`memory_search` | 词法检索已打通，精确查询强、语义改写弱 |

## 瓶颈清单（按优先级）

1. **无语义层**：同义改写 R@1 = 0，compare R@1 = 45%；需要 embedding + 混合检索（RRF）。
2. **无 reranker**：候选排序只靠 BM25，长文档与多跳问题弱。
3. **wiki 模式缺少评测**：目前评测只覆盖 evidence；wiki 的覆盖率、新鲜度、冲突率未量化。
4. **both 模式无权重/去重策略**：`allowedKinds` 直接合并，跨模式重复文档会挤占名额。
5. **分块与标题**：段落聚合 ≤1400 字符，标题不参与检索。
6. **答案层未评测**：faithfulness / citation correctness 未纳入回归。

## 每轮流程（60 分钟内）

1. 读本文件 + `docs/RAG链路评测-2026-11.md` + `git log -5`，确认上一轮结果。
2. 从瓶颈清单选 **一个** 可验证的小改进；先写一句假设（改什么、预期哪个指标动）。
3. 最小实现；保持 `tsc -p tsconfig.node.json` / `tsconfig.web.json` 与 `electron-vite build` 通过。
4. 跑 `node tools/rag-eval.mjs`（必要时先 `node tools/rag-corpus.mjs`）与受影响的能力脚本；记录改动前后数字。
5. 在下方「运行日志」追加一条（日期、假设、改动、指标、风险/回滚）。
6. 全绿才 `git add -A && git commit -m "mem: …" && git push origin main`；不绿则只记录、不留半成品。
7. 若改进需要用户决策（例如引入外部模型/依赖），在日志里标 `BLOCKED` 并停止本轮。

## 护栏

- 一轮最多一个提交；不重构无关模块；不改公开 API 的语义。
- 不删除用户记忆数据；SQLite 结构变更必须先备份 + 兼容旧库。
- 评测只使用隔离 profile（`.scratch/…`），不要动真实 `%APPDATA%/OpenFuture`。
- 不引入需要联网下载大模型/依赖的方案，除非用户明确批准。
- 每轮结束时若没有可交付改进，写明「本轮无可安全改进」而不是凑提交。
