# RAG 语义检索设计：切块、模型与本地硬件

> 2026-11-16 · 对应代码 `src/memory-host/chunk.ts`、`src/memory-host/retrieval.ts`、`tools/chunk-smoke.mjs`
> 评测口径见 [RAG-BEIR-TREC-COVID-2026-11.md](./RAG-BEIR-TREC-COVID-2026-11.md)、[RAG链路评测-2026-11.md](./RAG链路评测-2026-11.md)

## 1. 结论

- **切块**：采用「结构感知 + token 预算」方案。按 Markdown 结构（标题/段落）与句子边界切分，目标 352 token、上限 448 token、相邻块重叠 72 token；不超过 448 token 的文档整篇保留。CJK 与拉丁文本按统一 token 估算，避免中文块在 512 token 的 embedding 模型上被静默截断。
- **模型**：RTX 3050 Ti Laptop（4 GB 显存）可以跑 `bge-small-zh-v1.5`（24 M）+ `bge-reranker-base`（278 M）这一档；`bge-m3`（568 M）+ `bge-reranker-v2-m3` 属于上限，需要 8-bit 量化与分批，8k 上下文时容易 OOM。
- **顺序**：先接 embedding（检索召回），再接 cross-encoder reranker（重排）。两步都用现有评测脚本做 A/B，不靠感觉。
- **预期收益**：在真实 TREC-COVID 上，训练过的 cross-encoder 通常带来 5–12 个点 nDCG@10；embedding 主要改善同义改写与长尾语义查询（当前 paraphrase Recall@1 靠锚点，纯语义能力弱）。

## 2. 主流切块方法对比

| 方法 | 代表实现 | 粒度 | 优点 | 缺点 | 成本 |
| --- | --- | --- | --- | --- | --- |
| 固定长度 + overlap | LangChain `TokenTextSplitter` | 256–512 token | 简单、可预测 | 会断句、断语义 | 低 |
| 递归 / 结构感知 | `RecursiveCharacterTextSplitter`、LlamaIndex `SentenceSplitter` | 256–512 token，10–20% overlap | 保标题与段落结构，生产最常用 | 超长无标点段落退化 | 低 |
| 语义切块 | LlamaIndex `SemanticSplitterNodeParser`、Chonkie | 按相邻句向量相似度断点 | 边界自然 | 2–5× embedding 成本，阈值敏感 | 中高 |
| small-to-big / parent-child | 索引小块、返回父块 | 子块 200–400 token | 召回准 + 生成上下文全 | 需要父子映射与两套存储 | 中 |
| late chunking | Jina late chunking | 长上下文整篇编码后池化 | 指代与跨段上下文保留最好 | 需要 8k 上下文模型，工程复杂 | 高 |
| propositional / agentic | 研究方案 | 原子命题 | 精度高 | LLM 成本高、不可控 | 很高 |

我们选第二类（递归/结构感知）作为主方案：它在「效果 / 成本 / 可解释性」上最平衡，也是 LangChain、LlamaIndex 的默认推荐。small-to-big 作为后续可选增强（当前引用已经能回表到原文）。

## 3. 我们的切块实现

代码：`src/memory-host/chunk.ts`；自测：`node tools/chunk-smoke.mjs`。

### 3.1 参数

| 参数 | 值 | 说明 |
| --- | ---: | --- |
| `TARGET_TOKENS` | 352 | 打包目标，超过就开新块 |
| `MAX_TOKENS` | 448 | 硬上限；512 上下文留 12% 余量给 tokenizer 差异 |
| `OVERLAP_TOKENS` | 72 | 相邻块重叠（上一块最后一句） |
| `MIN_TOKENS` | 32 | 过短的末块并回前块 |

token 估算：`CJK 字符 × 1 + 拉丁词 × 1.3 + 标点 × 0.6`，向上取整。这个估算刻意偏保守——宁可块小一点，也不要在 512 窗口里被截断。

### 3.2 流程

1. 统一换行；空文本直接返回。
2. **整篇 ≤ 448 token → 单块返回**（短文档不切，避免索引碎片与重叠重复）。
3. 按空行切成 block，并记录原文偏移；Markdown 标题开启新段。
4. 普通段落按 token 预算装箱；放不下就 flush。
5. 超长段落按句子（`。！？!?`、`. `）切；单句仍超限时按其自身字符密度折算预算硬切。
6. 后处理：非首块加上一块最后一句作为重叠（≤72 token、合并后 ≤448 token、不以标题开头）。
7. 末尾小于 32 token 的块并回前块。

`TextChunk.quote` 是入库文本，`start`/`end` 是原文偏移，用于 `chars:a-b` 引用与回表高亮。

### 3.3 实测

- 合成文档 `storage-01.md`：355 字符 / 235 token → 1 块（`chars:0-354`）。旧实现按 1,400 字符打包也不切，但长段落会被字符硬切。
- TREC-COVID 摘要：平均 1,117 字符 ≈ 300 token → 多数单块；超长摘要（p95 2,318 字符）按句切 2–4 块。
- 100 文件 / 230 查询复跑（`tools/rag-eval.mjs`，hybrid-rerank）：Recall@1 99.1%、MRR 0.991、p50 9.2 ms，与切块 v2 之前持平——说明切块没有伤害短文档检索，同时长文档不再被字符硬切。

## 4. 模型选择与 3050 Ti（4 GB）可行性

显存预算 = 权重（fp16）+ 激活 + CUDA context（约 0.3 GB）。embedding 批量 32 × 512 token、rerank 批量 16 × (query+passage) 估算：

| 模型 | 参数量 | 维度 | 上下文 | fp16 权重 | 用途 | 4 GB 可行性 |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| `BAAI/bge-small-zh-v1.5` | 24 M | 512 | 512 | ~50 MB | 中文 embedding 首选 | 轻松，CPU 也能跑 |
| `intfloat/multilingual-e5-small` | 118 M | 384 | 512 | ~240 MB | 中英混合 | 轻松 |
| `BAAI/bge-base-zh-v1.5` | 102 M | 768 | 512 | ~210 MB | 质量升级 | 轻松（batch 32） |
| `jinaai/jina-embeddings-v2-base-zh` | 161 M | 768 | 8192 | ~330 MB | 长文档整篇编码 | 可行，8k 输入需 batch 4–8 |
| `BAAI/bge-m3` | 568 M | 1024 | 8192 | ~1.2 GB | 多语言 + 稀疏 + 稠密 | 可行但紧，建议 8-bit/batch 4 |
| `BAAI/bge-reranker-base` | 278 M | — | 512 | ~560 MB | rerank 首选 | 轻松（batch 16） |
| `BAAI/bge-reranker-v2-m3` | 568 M | — | 8192 | ~1.2 GB | 最强 rerank | 紧，8-bit/batch 8 |

粗略延迟（3050 Ti，fp16）：`bge-small` batch 32 约 5 ms；`bge-base` 约 12 ms；`reranker-base` batch 16 约 40 ms；`bge-m3` / `v2-m3` 约 120–200 ms。CPU 回退通常慢 5–10 倍，仍可用于离线索引。

**推荐档位**

- **P1（先做）**：`bge-small-zh-v1.5` 做稠密召回 + `bge-reranker-base` 重排 top-50。显存占用 < 1 GB，4 GB 卡余量充足。
- **P1.5**：换成 `bge-base-zh-v1.5` 或 `multilingual-e5-base`，用同一套评测确认收益。
- **P2（可选）**：`bge-m3` + `bge-reranker-v2-m3`，8-bit 量化，批量 4–8；若仍 OOM 就退回 P1.5。

运行时建议：`onnxruntime-node`（CUDA EP）或 `node-llama-cpp`（GGUF，Q8/Q4）。模型推理放在独立 utilityProcess，避免阻塞 Electron 主进程。

## 5. 接入路线

1. **向量持久化**：新增 `embeddings(entity_id, generation, dim, vector BLOB)`，或旁路 `<memoryDir>/vectors.bin`；写入时带 `vectorGeneration`，重建走后台任务 + 进度事件。
2. **编码缓存**：查询向量按 query 文本缓存；文档向量按 `vectorGeneration` 失效。
3. **融合**：替换 `retrieval.ts` 里的 `hashEmbedding` 为真实 embedding；权重沿用当前 `lexical 1 / dense 0.55 / qmd 1.1 / wiki 0.8`，先 A/B 再调。
4. **rerank**：只对融合后的 top-50 调用 cross-encoder；`OPENFUTURE_RERANK=off|heuristic|model` 三档，默认 `off`（当前真实语料上启发式 rerank 掉点）。
5. **兼容与回退**：无模型目录 / 加载失败时自动回退当前哈希向量 + 词法，不影响启动。
6. **评测**：`tools/rag-eval.mjs` 与 `tools/beir-trec-covid.mjs` 直接复用，报告按 `lexical / dense / dense+rerank` 三列对比。

环境变量建议：`OPENFUTURE_EMBED_MODEL`、`OPENFUTURE_RERANK_MODEL`、`OPENFUTURE_MODEL_DIR`、`OPENFUTURE_RETRIEVAL_MODE`。

## 6. 风险与限制

- **显存**：4 GB 卡跑 8k 上下文的 `bge-m3` 批次稍大就 OOM，必须量化 + 分批 + 超时保护。
- **模型分发**：权重 100–600 MB，首次使用需下载；离线安装包需要预置或提供镜像。
- **tokenizer 差异**：我们的 token 估算不是真实 tokenizer，448 上限留了 12% 余量；接入模型后应按实际 tokenizer 校准。
- **索引成本**：8,000 篇文档做 embedding 是分钟级任务，必须后台执行并给进度。
- **质量验证**：合成语料上的提升不代表真实场景；每次换模型都要在 TREC-COVID 切片上复跑。

## 8. 实现落地（2026-11-16）：bge-base-zh-v1.5 + bge-reranker-base

- 依赖：`@huggingface/transformers@3.8.1`（`onnxruntime-node` 走 CPU，不需要 GPU）。
- 模型：`Xenova/bge-base-zh-v1.5`（q8，102.9 MB，768 维，CLS pooling）、`Xenova/bge-reranker-base`（q8，279.3 MB）。
- 缓存：`<userData>/models`（`OPENFUTURE_MODEL_DIR` 可覆盖）。`src/memory-host/semantic.ts` 自带带 Range 续传的下载器：HuggingFace 官方下载器不支持断点续传，100 MB ONNX 断流后会截断，onnxruntime 报 `Protobuf parsing failed`。
- 索引：SQLite 新增 `semantic_vectors(hash, model, dim, vector)` 与 `semantic_docs(workspace_id, hash, kind, doc_id)`；内容哈希做键，换模型自动失效。导入时后台分批（16 条/批）嵌入，查询未就绪时回退哈希向量，`OPENFUTURE_SEMANTIC_WAIT=1` 可让导入等待索引完成（测试用）。
- 检索：词法 FTS5 + 锚点 + 稠密通道（余弦 > 0.3）经加权 RRF 融合；`hybrid-rerank` 对前 20 条用 cross-encoder 打分，按 `0.7 × sigmoid(logit) + 0.3 × 归一化 RRF` 重排。
- 开关：`OPENFUTURE_SEMANTIC=0` 关闭语义；`OPENFUTURE_RERANK=heuristic` 或 `off` 切回启发式/不重排；`OPENFUTURE_EMBED_MODEL` / `OPENFUTURE_RERANK_MODEL` / `OPENFUTURE_HF_ENDPOINT` 可换模型与镜像。
- 验证：`node tools/semantic-smoke.mjs`（嵌入近邻 0.775 vs 0.400，rerank 0.9999 vs 0.0000）。
- 合成语料（100 文件 / 240 查询，`RERANK=model node tools/rag-eval.mjs`）：

| 配置 | R@1 | R@10 | MRR | nDCG@10 | p50 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 哈希向量 + 启发式 rerank | 99.1% | 99.1% | 0.991 | 0.991 | 9.2 ms |
| bge-base-zh + bge-reranker-base | 97.1% | 100% | 0.981 | 0.981 | 2,646 ms |

  分组：exact 100%、value 97%、compare 80%（启发式 100%）、paraphrase 100%、title 100%。结论：在「精确代码 + 唯一阈值」的锚点型查询上，cross-encoder 会把同时命中代码的干扰文档排到前面，R@1 反而降 2 个点，延迟高约 300 倍；R@10 提到 100% 说明语义通道扩大了召回面。
- 真实语料（TREC-COVID 8k 篇）语义复跑未完成：CPU 嵌入 8,000 篇在导入阶段就要约 40 分钟（3 篇/秒，且与后台嵌入争 CPU），超出本轮时间预算；脚本已支持 `POOL_SIZE`/`SEMANTIC_WAIT_MS`，可在夜间运行。
- 限制：CPU 推理，rerank 20 条约 1–3 秒；首次下载约 380 MB；`electron-builder.yml` 当前 `asar: false`，安装包需要把 `node_modules/onnxruntime-node` 一起带上（原生 `.node` 不能进 asar）。

### 8.1 检索指标与向量索引面板（2026-11-16 追加）

- 表 `retrieval_events(workspace_id, at, query, hits, top_score, duration_ms, engine, mode)`：每次 `search` RPC（面板检索与 Agent `memory_search` 共用）都记录一行，按 workspace 保留最近 500 条。
- `memoryMetrics()` 返回总次数、近 200 次命中率（hits>0）、p50/p95、最近 8 条；`memoryEmbedPending()` 返回待嵌入文档数并在后台补索引。
- 面板「总览」显示 `向量文档 x / search_index 总数`、检索次数、命中率、p50/p95、模型就绪状态与「生成向量索引」按钮；「检索」页显示检索记录列表；打开面板后每 5 秒轮询一次指标。
- memory-host 启动时 `warmSemanticCaches()`：按 `semantic_docs` 里的 workspace 预热 embedder、从 SQLite 水合向量缓存（不重新嵌入），并按 `OPENFUTURE_RERANK` 预热 reranker。
- 下载器改为流式落盘 + 45 秒空闲超时：先前 `response.arrayBuffer()` 在 120 秒超时后丢弃全部字节，279 MB 的 reranker 在慢速网络上永远无法推进；现在每次尝试保留已下载字节，下次 Range 续传。
- 实测（真实 userData）：`memoryEmbedPending()` → `{pending:23}`，随后 `semanticDocCount=23`、`semanticReady=true`；一次真实对话触发 2 次 `memory_search`，面板显示「检索 3 次 · 命中率 100% · p50 12 ms」；reranker 就绪后论文查询 `durationMs=5030`、`topScore=0.971`（此前启发式 55 ms / 0.016）。
