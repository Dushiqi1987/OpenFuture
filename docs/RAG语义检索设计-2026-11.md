# RAG 语义检索设计：切块、模型与本地硬件

> 2026-11-16 · 对应代码 `src/memory-host/chunk.ts`、`src/memory-host/retrieval.ts`、`tools/chunk-smoke.mjs`
> 评测口径见 [RAG-BEIR-TREC-COVID-2026-11.md](./RAG-BEIR-TREC-COVID-2026-11.md)、[RAG链路评测-2026-11.md](./RAG链路评测-2026-11.md)

## 1. 结论

- **切块**：采用「结构感知 + token 预算」方案。按 Markdown 结构（标题/段落）与句子边界切分，目标 352 token、上限 448 token、相邻块重叠 72 token；不超过 448 token 的文档整篇保留。CJK 与拉丁文本按统一 token 估算，避免中文块在 512 token 的 embedding 模型上被静默截断。
- **模型**：RTX 3050 Ti Laptop（4 GB 显存）可以跑 `bge-small-zh-v1.5`（24 M）+ `bge-reranker-base`（278 M）这一档；`bge-m3`（568 M）+ `bge-reranker-v2-m3` 属于上限，需要 8-bit 量化与分批，8k 上下文时容易 OOM。
- **顺序**：先接 embedding（检索召回），再接 cross-encoder reranker（重排）。两步都用现有评测脚本做 A/B，不靠感觉。
- **预期收益**：在真实 TREC-COVID 上，训练过的 cross-encoder 通常带来 5–12 个点 nDCG@10；embedding 主要改善同义改写与长尾语义查询（当前 paraphrase Recall@1 靠锚点，纯语义能力弱）。

## 2. 主流切块方法对比

| 方法 | 代表实现 | 粒度 | 优点 | 缺点 | 成本 |
| --- | --- | --- | --- | --- | --- |
| 固定长度 + overlap | LangChain `TokenTextSplitter` | 256–512 token | 简单、可预测 | 会断句、断语义 | 低 |
| 递归 / 结构感知 | `RecursiveCharacterTextSplitter`、LlamaIndex `SentenceSplitter` | 256–512 token，10–20% overlap | 保标题与段落结构，生产最常用 | 超长无标点段落退化 | 低 |
| 语义切块 | LlamaIndex `SemanticSplitterNodeParser`、Chonkie | 按相邻句向量相似度断点 | 边界自然 | 2–5× embedding 成本，阈值敏感 | 中高 |
| small-to-big / parent-child | 索引小块、返回父块 | 子块 200–400 token | 召回准 + 生成上下文全 | 需要父子映射与两套存储 | 中 |
| late chunking | Jina late chunking | 长上下文整篇编码后池化 | 指代与跨段上下文保留最好 | 需要 8k 上下文模型，工程复杂 | 高 |
| propositional / agentic | 研究方案 | 原子命题 | 精度高 | LLM 成本高、不可控 | 很高 |

我们选第二类（递归/结构感知）作为主方案：它在「效果 / 成本 / 可解释性」上最平衡，也是 LangChain、LlamaIndex 的默认推荐。small-to-big 作为后续可选增强（当前引用已经能回表到原文）。

## 3. 我们的切块实现

代码：`src/memory-host/chunk.ts`；自测：`node tools/chunk-smoke.mjs`。

### 3.1 参数

| 参数 | 值 | 说明 |
| --- | ---: | --- |
| `TARGET_TOKENS` | 352 | 打包目标，超过就开新块 |
| `MAX_TOKENS` | 448 | 硬上限；512 上下文留 12% 余量给 tokenizer 差异 |
| `OVERLAP_TOKENS` | 72 | 相邻块重叠（上一块最后一句） |
| `MIN_TOKENS` | 32 | 过短的末块并回前块 |

token 估算：`CJK 字符 × 1 + 拉丁词 × 1.3 + 标点 × 0.6`，向上取整。这个估算刻意偏保守——宁可块小一点，也不要在 512 窗口里被截断。

### 3.2 流程

1. 统一换行；空文本直接返回。
2. **整篇 ≤ 448 token → 单块返回**（短文档不切，避免索引碎片与重叠重复）。
3. 按空行切成 block，并记录原文偏移；Markdown 标题开启新段。
4. 普通段落按 token 预算装箱；放不下就 flush。
5. 超长段落按句子（`。！？!?`、`. `）切；单句仍超限时按其自身字符密度折算预算硬切。
6. 后处理：非首块加上一块最后一句作为重叠（≤72 token、合并后 ≤448 token、不以标题开头）。
7. 末尾小于 32 token 的块并回前块。

`TextChunk.quote` 是入库文本，`start`/`end` 是原文偏移，用于 `chars:a-b` 引用与回表高亮。

### 3.3 实测

- 合成文档 `storage-01.md`：355 字符 / 235 token → 1 块（`chars:0-354`）。旧实现按 1,400 字符打包也不切，但长段落会被字符硬切。
- TREC-COVID 摘要：平均 1,117 字符 ≈ 300 token → 多数单块；超长摘要（p95 2,318 字符）按句切 2–4 块。
- 100 文件 / 230 查询复跑（`tools/rag-eval.mjs`，hybrid-rerank）：Recall@1 99.1%、MRR 0.991、p50 9.2 ms，与切块 v2 之前持平——说明切块没有伤害短文档检索，同时长文档不再被字符硬切。

## 4. 模型选择与 3050 Ti（4 GB）可行性

显存预算 = 权重（fp16）+ 激活 + CUDA context（约 0.3 GB）。embedding 批量 32 × 512 token、rerank 批量 16 × (query+passage) 估算：

| 模型 | 参数量 | 维度 | 上下文 | fp16 权重 | 用途 | 4 GB 可行性 |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| `BAAI/bge-small-zh-v1.5` | 24 M | 512 | 512 | ~50 MB | 中文 embedding 首选 | 轻松，CPU 也能跑 |
| `intfloat/multilingual-e5-small` | 118 M | 384 | 512 | ~240 MB | 中英混合 | 轻松 |
| `BAAI/bge-base-zh-v1.5` | 102 M | 768 | 512 | ~210 MB | 质量升级 | 轻松（batch 32） |
| `jinaai/jina-embeddings-v2-base-zh` | 161 M | 768 | 8192 | ~330 MB | 长文档整篇编码 | 可行，8k 输入需 batch 4–8 |
| `BAAI/bge-m3` | 568 M | 1024 | 8192 | ~1.2 GB | 多语言 + 稀疏 + 稠密 | 可行但紧，建议 8-bit/batch 4 |
| `BAAI/bge-reranker-base` | 278 M | — | 512 | ~560 MB | rerank 首选 | 轻松（batch 16） |
| `BAAI/bge-reranker-v2-m3` | 568 M | — | 8192 | ~1.2 GB | 最强 rerank | 紧，8-bit/batch 8 |

粗略延迟（3050 Ti，fp16）：`bge-small` batch 32 约 5 ms；`bge-base` 约 12 ms；`reranker-base` batch 16 约 40 ms；`bge-m3` / `v2-m3` 约 120–200 ms。CPU 回退通常慢 5–10 倍，仍可用于离线索引。

**推荐档位**

- **P1（先做）**：`bge-small-zh-v1.5` 做稠密召回 + `bge-reranker-base` 重排 top-50。显存占用 < 1 GB，4 GB 卡余量充足。
- **P1.5**：换成 `bge-base-zh-v1.5` 或 `multilingual-e5-base`，用同一套评测确认收益。
- **P2（可选）**：`bge-m3` + `bge-reranker-v2-m3`，8-bit 量化，批量 4–8；若仍 OOM 就退回 P1.5。

运行时建议：`onnxruntime-node`（CUDA EP）或 `node-llama-cpp`（GGUF，Q8/Q4）。模型推理放在独立 utilityProcess，避免阻塞 Electron 主进程。

## 5. 接入路线

1. **向量持久化**：新增 `embeddings(entity_id, generation, dim, vector BLOB)`，或旁路 `<memoryDir>/vectors.bin`；写入时带 `vectorGeneration`，重建走后台任务 + 进度事件。
2. **编码缓存**：查询向量按 query 文本缓存；文档向量按 `vectorGeneration` 失效。
3. **融合**：替换 `retrieval.ts` 里的 `hashEmbedding` 为真实 embedding；权重沿用当前 `lexical 1 / dense 0.55 / qmd 1.1 / wiki 0.8`，先 A/B 再调。
4. **rerank**：只对融合后的 top-50 调用 cross-encoder；`OPENFUTURE_RERANK=off|heuristic|model` 三档，默认 `off`（当前真实语料上启发式 rerank 掉点）。
5. **兼容与回退**：无模型目录 / 加载失败时自动回退当前哈希向量 + 词法，不影响启动。
6. **评测**：`tools/rag-eval.mjs` 与 `tools/beir-trec-covid.mjs` 直接复用，报告按 `lexical / dense / dense+rerank` 三列对比。

环境变量建议：`OPENFUTURE_EMBED_MODEL`、`OPENFUTURE_RERANK_MODEL`、`OPENFUTURE_MODEL_DIR`、`OPENFUTURE_RETRIEVAL_MODE`。

## 6. 风险与限制

- **显存**：4 GB 卡跑 8k 上下文的 `bge-m3` 批次稍大就 OOM，必须量化 + 分批 + 超时保护。
- **模型分发**：权重 100–600 MB，首次使用需下载；离线安装包需要预置或提供镜像。
- **tokenizer 差异**：我们的 token 估算不是真实 tokenizer，448 上限留了 12% 余量；接入模型后应按实际 tokenizer 校准。
- **索引成本**：8,000 篇文档做 embedding 是分钟级任务，必须后台执行并给进度。
- **质量验证**：合成语料上的提升不代表真实场景；每次换模型都要在 TREC-COVID 切片上复跑。

## 8. 实现落地（2026-11-16）：bge-base-zh-v1.5 + bge-reranker-base

- 依赖：`@huggingface/transformers@3.8.1`（`onnxruntime-node` 走 CPU，不需要 GPU）。
- 模型：`Xenova/bge-base-zh-v1.5`（q8，102.9 MB，768 维，CLS pooling）、`Xenova/bge-reranker-base`（q8，279.3 MB）。
- 缓存：`<userData>/models`（`OPENFUTURE_MODEL_DIR` 可覆盖）。`src/memory-host/semantic.ts` 自带带 Range 续传的下载器：HuggingFace 官方下载器不支持断点续传，100 MB ONNX 断流后会截断，onnxruntime 报 `Protobuf parsing failed`。
- 索引：SQLite 新增 `semantic_vectors(hash, model, dim, vector)` 与 `semantic_docs(workspace_id, hash, kind, doc_id)`；内容哈希做键，换模型自动失效。导入时后台分批（16 条/批）嵌入，查询未就绪时回退哈希向量，`OPENFUTURE_SEMANTIC_WAIT=1` 可让导入等待索引完成（测试用）。
- 检索：词法 FTS5 + 锚点 + 稠密通道（余弦 > 0.3）经加权 RRF 融合；`hybrid-rerank` 对前 20 条用 cross-encoder 打分，按 `0.7 × sigmoid(logit) + 0.3 × 归一化 RRF` 重排。
- 开关：`OPENFUTURE_SEMANTIC=0` 关闭语义；`OPENFUTURE_RERANK=heuristic` 或 `off` 切回启发式/不重排；`OPENFUTURE_EMBED_MODEL` / `OPENFUTURE_RERANK_MODEL` / `OPENFUTURE_HF_ENDPOINT` 可换模型与镜像。
- 验证：`node tools/semantic-smoke.mjs`（嵌入近邻 0.775 vs 0.400，rerank 0.9999 vs 0.0000）。
- 合成语料（100 文件 / 240 查询，`RERANK=model node tools/rag-eval.mjs`）：

| 配置 | R@1 | R@10 | MRR | nDCG@10 | p50 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 哈希向量 + 启发式 rerank | 99.1% | 99.1% | 0.991 | 0.991 | 9.2 ms |
| bge-base-zh + bge-reranker-base | 97.1% | 100% | 0.981 | 0.981 | 2,646 ms |

  分组：exact 100%、value 97%、compare 80%（启发式 100%）、paraphrase 100%、title 100%。结论：在「精确代码 + 唯一阈值」的锚点型查询上，cross-encoder 会把同时命中代码的干扰文档排到前面，R@1 反而降 2 个点，延迟高约 300 倍；R@10 提到 100% 说明语义通道扩大了召回面。
- 真实语料（TREC-COVID 8k 篇）语义复跑未完成：CPU 嵌入 8,000 篇在导入阶段就要约 40 分钟（3 篇/秒，且与后台嵌入争 CPU），超出本轮时间预算；脚本已支持 `POOL_SIZE`/`SEMANTIC_WAIT_MS`，可在夜间运行。
- 限制：CPU 推理，rerank 20 条约 1–3 秒；首次下载约 380 MB；`electron-builder.yml` 当前 `asar: false`，安装包需要把 `node_modules/onnxruntime-node` 一起带上（原生 `.node` 不能进 asar）。

### 8.1 检索指标与向量索引面板（2026-11-16 追加）

- 表 `retrieval_events(workspace_id, at, query, hits, top_score, duration_ms, engine, mode)`：每次 `search` RPC（面板检索与 Agent `memory_search` 共用）都记录一行，按 workspace 保留最近 500 条。
- `memoryMetrics()` 返回总次数、近 200 次命中率（hits>0）、p50/p95、最近 8 条；`memoryEmbedPending()` 返回待嵌入文档数并在后台补索引。
- 面板「总览」显示 `向量文档 x / search_index 总数`、检索次数、命中率、p50/p95、模型就绪状态与「生成向量索引」按钮；「检索」页显示检索记录列表；打开面板后每 5 秒轮询一次指标。
- memory-host 启动时 `warmSemanticCaches()`：按 `semantic_docs` 里的 workspace 预热 embedder、从 SQLite 水合向量缓存（不重新嵌入），并按 `OPENFUTURE_RERANK` 预热 reranker。
- 下载器改为流式落盘 + 45 秒空闲超时：先前 `response.arrayBuffer()` 在 120 秒超时后丢弃全部字节，279 MB 的 reranker 在慢速网络上永远无法推进；现在每次尝试保留已下载字节，下次 Range 续传。
- 实测（真实 userData）：`memoryEmbedPending()` → `{pending:23}`，随后 `semanticDocCount=23`、`semanticReady=true`；一次真实对话触发 2 次 `memory_search`，面板显示「检索 3 次 · 命中率 100% · p50 12 ms」；reranker 就绪后论文查询 `durationMs=5030`、`topScore=0.971`（此前启发式 55 ms / 0.016）。

### 8.2 检索调优与默认策略（2026-11-17，2026-11-17 恢复后复测）

- 评测台 `tools/rag-bench.mjs`：用假 `ParentPort` 直接在 Node 里跑构建产物 `out/main/memory-host.js`，不启动 Electron；TREC 用 `VACUUM INTO` 复制的真实库快照（`.scratch/bench/memory/memory.sqlite`），合成语料用 `importSource` RPC 导入（`.scratch/bench/synthetic-memory`，100 篇 / 240 查询）。输出 R@k、`recallCap10`、nDCG@10、MRR@10、p50/p95。注意 bench 自带 `OPENFUTURE_RETRIEVAL_MODE` 默认 `hybrid`，验证代码默认值时要显式传 `hybrid-rerank`。
- TREC-COVID 8k（15 queries，平均 gold 232 篇/查询，R@10 数学上限约 4%，只看 nDCG/MRR/p50）：

| 配置 | nDCG@10 | MRR@10 | p50 | p95 |
| --- | --- | --- | --- | --- |
| lexical（仅词法通道 + PRF + anchors） | 0.7039 | 0.8667 | 210 ms | 333 ms |
| hybrid（dense 0.75，更便宜的备选） | 0.6942 | 0.8667 | 256 ms | 385 ms |
| **hybrid-rerank（默认，启发式重排）** | **0.7033** | **0.9667** | **333 ms** | **574 ms** |
| hybrid + cross-encoder（top-5、w=0.3、全文） | 0.6993 | 0.9333 | 5.0 s | — |

- 中文合成语料（100 篇 / 240 查询）：lexical 0.9851 / MRR 0.9812 / p50 9 ms；hybrid 0.9851 / 0.9812 / 26 ms；**hybrid-rerank 0.9928 / MRR 0.9917 / p50 34 ms**；cross-encoder 0.9922 / 1.6 s。中文问题不需要模型重排，启发式（词面覆盖）已经足够。
- 语言自适应锚点权重：中文查询是一整串无空格文本，literal anchor 是主词法通道；英文靠 `search_words` 的 BM25。默认按 `hasCjk(query)` 取 0.8 / 0.45（`OPENFUTURE_ANCHOR_WEIGHT` 可强制覆盖）。该策略让合成语料从 0.5726（anchor 0.45）恢复到 **0.9851**，TREC 仍保持 0.70+。
- 扫描结果（TREC，其余默认）：PRF 权重 0.3 → 0.6942、0.6 → 0.6937、**1.0 → 0.7099**（k=20、anchor 0.45 时）；`RRF_K` 20 → 0.6765、60 → 0.6628、100 → 0.6656；`CANDIDATE_SCALE` 2/3/5 → 0.6847/0.6847/0.6850（无收益）；dense 权重 0.75 → 0.6847、1.2 → 0.6654、2.0 → 0.309、3.0 → 0.1765（语义过强会压垮词法排序）。
- 短语邻近通道（查询 bigram 在正文中相邻出现，`OPENFUTURE_PHRASE_WEIGHT` 默认 0）：开启后 TREC 0.6688 → 0.6516，只有 MRR 升到 0.9222，已默认关闭。
- 失败尝试（已回退/默认关）：trigram BM25 与词通道融合（0.29–0.34）；anchor 收窄成只匹配数字/下划线/全大写（0.31）；rerank 只喂 480 字符窗口（0.35）；CJK 查询强制启用 trigram（合成不变）；PRF 在中文上生效（0.9958 → 0.7426，已 gate）；dense 权重 0.85 以上（中文 0.9958 → 0.7174）。
- 数字锚点：英文用 `' ' || text_lower || ' '` 空格填充匹配（避免 `20` 命中 `200`）；中文数字常与单位连写（`10秒`），按 `hasCjk(query)` 退回纯子串匹配。
- 结果去重：同一资料多个 chunk 只保留最佳一条（`OPENFUTURE_MAX_PER_SOURCE`，默认 1），截断到 limit 放在去重之后；避免长文档挤占 top-10 展示位。
- 默认值：`RETRIEVAL_MODE` 默认 **`hybrid-rerank`**，`OPENFUTURE_PRF` 默认 **1.0**，`OPENFUTURE_RRF_K` 默认 **20**，`OPENFUTURE_ANCHOR_WEIGHT` 缺省按语言自适应，`OPENFUTURE_RERANK` 仍默认 `heuristic`（cross-encoder 需显式 `model`）。
- 索引重构：新增 `search_words`（`fts5(tokenize='porter unicode61')`）英文词干通道；`search_docs` 普通镜像表（rowid 与 FTS5 对齐，删除 O(1)）承载 `text_lower`；锚点扫描由「JS 遍历 8.7k 行重建字符串」改为 `instr(text_lower, ?)` SQL，单查询从约 1 s 降到 120 ms；FTS5 的 `search_index` 不再参与 JOIN（8.7k 行时会让 memory-host 事件循环冻结数分钟）。
- 结论：收益主要来自 **词干 + SQL 锚点词法通道 + PRF + 语言自适应权重**（legacy 0.349 → 0.704）；语义 dense 只作补充（TREC 上略拉低、中文几乎无增益）；cross-encoder 质量增益 +0.000（相对默认）却慢 15 倍，保留为显式质量模式。

| lexical + 关闭 literal anchors（`OPENFUTURE_ANCHOR_WEIGHT=0`） | **0.6797** | 0.5272 | 0.8227 | 0.6394 | 426 ms |
| hybrid（dense 0.75） | 0.6478 | 0.4883 | 0.7971 | 0.6056 | 265 ms |
| hybrid-rerank（默认） | 0.6482 | 0.5006 | 0.7726 | 0.6156 | 378 ms |

- 结论：SciFact 上 **literal anchor 是负收益**（claim 很短，锚点命中放大偶然词面重叠），而 TREC 上正收益（长问句 + 232 篇 gold/查询）；`OPENFUTURE_ANCHOR_WEIGHT=0` 可整体关闭。dense 在 SciFact 上没有增益（bge-base-zh 对英文科学 claim 的语义区分不足），印证「语义通道主要覆盖同义改写长尾」。
- 切块粒度消融（中文合成语料 100 篇 / 240 查询，lexical）：`TARGET=128/MAX=192` → nDCG 0.9681（掉 1.7 点）；`TARGET=352`（默认）与 `TARGET=640` 并列 0.9851。短文档场景下 352–640 无差别，**过小切块（<200 token）明显伤召回**，与「embedding 512 token 上限」的约束一致。新增 `OPENFUTURE_CHUNK_TARGET/MAX/OVERLAP/MIN` 便于复现。
- 跨语言实测（真实 8k 医学库，面板 CDP 调用）：英文问句 top1 命中正确文献（胆囊切除 2.2 s / remdesivir 278 ms / spike 抗体 234 ms，分数 18–47）；中文问句（「淋巴细胞减少与预后」「儿童多系统炎症综合征」）top1 分数骤降到 0.17–5.4，命中靠 dense 而非词法——**中文问 / 英文文档仍是弱项**，后续要么换多语 embedding（bge-m3 / e5-multilingual），要么在查询侧做术语翻译扩展。
- 真实对话查询样本来自 `<userData>/pi/agent/sessions/*.jsonl` 的 user 消息（多为产品类问题，如「帮我写一个鹈鹕骑单车得网页」），与医学库高度不相关，只用于确认「无关查询不会伪造记忆命中」：这类查询 top1 分数接近 0.17，符合预期。

### 8.4 中文问英文库：术语翻译扩展与语言自适应重排（2026-11-17 追加）

§8.3 的跨语言实测暴露了最大短板：中文问句在英文库里 top1 分数只有 0.17–5.4。新增 `trec-zh` 评测集量化它：从 TREC-COVID 的 10 条查询人工译成中文、保留原 qrels，在同一个 8k 英文库上跑。

| 配置 | nDCG@10 | R@1 | R@10 | MRR@10 | p50 |
| --- | --- | --- | --- | --- | --- |
| 翻译前 hybrid | 0.2064 | 0.001 | 0.017 | 0.359 | 223 ms |
| 翻译前 hybrid-rerank | 0.2369 | 0.002 | 0.017 | 0.462 | 246 ms |
| 翻译扩展 w=0.8 | 0.4120 | 0.002 | 0.029 | 0.549 | 294 ms |
| 翻译扩展 w=1.2（默认） | **0.4622** | 0.002 | 0.035 | 0.566 | 291 ms |
| 扩展 + 自适应重排（第八轮默认） | **0.6671** | 0.005 | 0.042 | **1.000** | 287 ms |

实现：

- `src/memory-host/bilingual.ts`：约 55 条医学/疫情领域中文→英文词表（按中文长度降序匹配，长词优先），`bilingualQueryTerms()` 抽出英文词（≤24）。只在查询含 CJK 时触发，英文查询与中文库完全不受影响。
- `searchMemory`：`hasCjk(query)` 时把翻译词跑 `search_words`（porter 词干索引）得 `bilingualHits`，按 `OPENFUTURE_BILINGUAL_WEIGHT`（默认 1.2）融进 RRF。
- 语言自适应重排：翻译扩展命中（`bilingualHits.length > 0`）时说明这是「中文问英文库」，此时启发式重排没有词面可打分、反而打乱翻译 BM25 的顺序——跳过重排，并像 `hybrid` 一样过滤已在词法列表里的 dense 项。于是中文跨语言走 hybrid 顺序（第八轮加入维生素/疫苗品牌词后 0.6671、MRR 1.000），中文同语言/英文查询仍走 hybrid-rerank（合成 0.9928、TREC 0.7167 不变）。`OPENFUTURE_ADAPTIVE_RERANK=0` 可关闭。

失败的尝试（均已回退）：加大 dense 权重（1.2→0.4102、1.8→0.3353、2.6→0.3219）；用 dense top-3 文档做中文查询的伪相关反馈（0.3411–0.4212）；权重 0.8 欠权（0.4120）、1.3–1.6 过权（0.4597–0.4445）。

局限：中文查询的 R@1 仍接近 0（0.0047）——目标文档在 top-10 里可见但首条常被覆盖；数字/命名实体（「减少 40%」「非裔美国人」）无法被词表覆盖，需要真正的多语 embedding（bge-m3）或查询翻译模型。

### 8.5 第八轮：claim 感知锚点与词通道权重（2026-11-17 追加）

两个改动的共同观察：**锚点的价值取决于查询形态**。TREC 的疑问句里 anchor（原词字面匹配）能压住 dense 的语义漂移；SciFact 的 claim 是陈述句，词面重叠常是偶然的，anchor 反而放大噪声。

| 语料 | 改前 nDCG@10 | 改后 nDCG@10 | MRR@10 | p50 |
| --- | --- | --- | --- | --- |
| TREC-COVID 8k（15 查询） | 0.7033 | **0.7167** | 0.967 | 332 ms |
| BEIR SciFact（300 查询） | 0.6532 | **0.6677** | 0.633 | 412 ms |
| 中文合成（240 查询） | 0.9928 | 0.9928 | 0.992 | 36 ms |
| trec-zh 中文问英文库（10 查询） | 0.6064 | **0.6671** | 1.000 | 287 ms |

改动：

- `isClaimQuery(query)`：无 `?`/`？` 且不以 how/what/which/who/is/are/does/can… 开头 → 陈述式 claim。`OPENFUTURE_ANCHOR_WEIGHT` 未显式设置时：CJK 0.8、claim 0（关闭锚点列表）、其余问句 0.45。SciFact 上实测与显式 `OPENFUTURE_ANCHOR_WEIGHT=0` 等价。
- `OPENFUTURE_WORD_WEIGHT` 默认 1.2 → **1.4**：词干通道在 TREC 上 1.0/1.2/1.4/1.7 = 0.6751/0.7033/0.7167/0.7162；SciFact 与合成语料在 1.4 下变化在噪声内。
- 中文词表补充 `维生素 d`/`维生素`/`辉瑞`/`莫德纳`/`阿斯利康`/`中和抗体`/`免疫逃逸`/`长期症状` 等；trec-zh 从 0.6064 提到 0.6662（维生素 D 那条查询从 0 命中变为 nDCG 0.77）。
- 进一步扫描：dense 0.7 让 TREC 到 0.7183，但 trec-zh 从 0.6671 掉到 0.6628、MRR 1.0→0.95，不采纳；RRF k 14/30 均低于 20。

失败的尝试（未采纳）：trec-zh 上 cross-encoder 重排（c10/c20 top5）反而 0.4583、MRR 0.783，且 p50 1.7–1.9 s——bge-reranker-base 对「中文查询 × 英文文档」的顺序判断弱于翻译 BM25。

局限：中文 R@1 仍 0.005（TREC qrels 平均 232 篇/查询，R@1 统计上接近 0）；claim 检测依赖英文疑问词前缀，其他语言需另定规则。

### 8.6 第九轮：claim 专属 PRF 与中文 bge 指令（2026-11-17 追加）

沿用 §8.5 的「查询形态」视角做两处细化。

**claim 用低 PRF。** SciFact 上扫描 `OPENFUTURE_PRF`：0 → 0.6677、0.5 → **0.6774**、0.7 → 0.6751、1.0 → 0.6677、1.5 → 0.6640；TREC 疑问句则 1.0 最好（0.7167），0.7 → 0.7146、0.5 → 0.7072。于是默认值改为形态自适应：`isClaimQuery(query) ? 0.5 : 1.0`，显式 env 仍优先。

**中文 bge 检索指令。** bge 官方建议中文检索查询加前缀「为这个句子生成表示以用于检索相关文章：」。实测：
- 中文同语言（合成语料）：0.9928 → **0.9958**（R@1 0.9458 → 0.9542）；
- 中文问英文库（trec-zh）：0.6671 → 0.6482，反而掉——指令把中文查询推向「中文语义空间」，与英文文档更远。
因此 `embedQuery(text, instruction)` 由 `searchMemory` 决定：只有**没有触发翻译扩展**的 CJK 查询才加指令；跨语言查询不加。`OPENFUTURE_EMBED_INSTRUCTION=0` 可整体关闭。

第九轮终值：TREC 0.7167（p50 342 ms）、SciFact **0.6774**（p50 392 ms）、中文合成 **0.9958**（p50 41 ms）、trec-zh 0.6671（MRR 1.000，p50 283 ms）。

### 8.7 第十轮：切换 multilingual-e5-small（2026-11-17 追加）

**动机**：trec-zh（中文问英文库）在 bge-base-zh 上只有 0.606，R@10 仅 3.9%；bge 是中文单语模型，英文语义空间弱。换用多语模型才能真正解决跨语言召回。

**实现**（`src/memory-host/semantic.ts`）：

- 默认 `EMBED_MODEL` 改为 `Xenova/multilingual-e5-small`（384 维，q8 118 MB）。
- e5 需要 **mean pooling**（按 attention mask 平均），bge 是 CLS pooling；新增 `poolMean(output, inputs, count)`，按 `OPENFUTURE_EMBED_POOL`（默认按模型名自动：e5 → mean，其他 → cls）选择。
- e5 需要前缀 `query: ` / `passage: `；`OPENFUTURE_QUERY_PREFIX` / `OPENFUTURE_DOC_PREFIX` 默认按模型名自动设置，`embedTexts(texts, kind)` 按 kind 加前缀。
- bge 的中文检索指令与新模型不兼容：`INSTRUCTION_ENABLED` 默认在 e5 上关闭（`OPENFUTURE_EMBED_INSTRUCTION` 可显式覆盖）。
- 模型文件仍按 `OPENFUTURE_MODEL_DIR` 缓存；切换模型会让 `semantic_vectors.model` 不匹配，旧向量自动失效，需要重新嵌入（离线 `.scratch/embed-offline.mjs` 9.4 块/秒，8.7k 约 15 分钟；应用内后台补齐同速）。

**四套语料对照（同一评测台、默认 hybrid-rerank/heuristic）**：

| 语料 | bge-base-zh | e5-small | 变化 | p50 |
| --- | --- | --- | --- | --- |
| TREC-COVID 8k（15 询） | 0.7167 | **0.7329** | +0.016 | 339 ms |
| BEIR SciFact（300 询） | 0.6774 | **0.6967** | +0.019 | 376 ms |
| 中文合成（240 询） | 0.9958 | **0.9958** | 0 | 29 ms |
| trec-zh 中文问英文（10 询） | 0.6064 | **0.6720** | +0.066 | 302 ms |

R@1/R@10 也同步改善：SciFact R@1 0.563 / R@10 0.807（bge 0.554 / 0.780）；trec-zh R@10 0.043（bge 0.039），MRR 仍 1.000。中文同语言不掉点，因为 e5 多语训练覆盖中文，且中文库仍主要靠词法通道。

**风险与限制**：

- 切换默认模型是一次性迁移成本（重嵌）；库大时建议离线跑或用面板「生成向量索引」。
- bge-reranker-base 未替换（中英双语，够用）；若换多语 reranker（如 bge-reranker-v2-m3）需再评。
- 中文 R@1 仍低（trec-zh 0.005）：证据级 R@1 需要 rerank 或更细的段级检索，本轮未动。


### 8.8 第十一轮：dense 权重与 claim 参数复核（2026-11-17 追加）

换 e5 后重新扫描通道权重，结论与 bge 时期不同：多语向量对 CJK 更稳，dense 可以更高。

| dense 权重 | TREC | trec-zh | 合成中文 | SciFact |
| --- | --- | --- | --- | --- |
| 0.75（旧默认） | 0.7329 | 0.6720 | 0.9958 | 0.6967 |
| 0.85 | 0.7368 | 0.6834 | 0.9958 | 0.6987 |

### 8.9 第十二轮：检索回归门禁与负结果（2026-11-17 追加）

- 新增 `tools/rag-regress.mjs`：依次跑四套语料（各自的 e5 快照），对照下限 TREC 0.735 / trec-zh 0.68 / SciFact 0.69 / 中文合成 0.99，任一低于下限或跑不出结果即非零退出；`--only=` 可只跑部分语料。首跑结果：0.7469 / 0.6948 / 0.6992 / 0.9958，全部通过。
- 修掉一个静默回退：`tools/rag-bench.mjs` 原来默认指向 bge 快照（`memory/`、`scifact-memory/`、`synthetic-memory/`）。默认模型换成 e5 后，这些快照里没有 e5 向量，dense 会**静默退回哈希向量**、指标看似正常实际不可比。现在默认指向 `memory-e5/`、`scifact-e5/`、`synthetic-e5/`，并在 `semanticDocCount === 0` 时打印警告。
- 负结果一：cross-encoder 在 e5 上仍然不划算。TREC c10 / top5 / w0.3 只有 nDCG@10 0.526（默认 0.7469），且 p50 1.1 s；与 bge 时期「0.699 但慢 5 秒」相比进一步变差，继续默认关闭。
- 负结果二：把启发式重排需要的文档正文改成一次 `IN (...)` 批量取（150 个候选），profile 里 `merged` 从 136 ms 降到 86 ms，但整体 p50 反而从 339 ms 升到 377–385 ms（重复三次），原因是批量语句每次重新编译、且候选更多时收益被 anchors 的 100–125 ms 掩盖。已回退，保持逐条 `documentText`。
- 当前 profile（TREC，单查询）：anchors 100–125 ms、words 43–70 ms、dense 31–57 ms、prf 44 ms、refs ≈80 ms、merged 86–136 ms；anchors 的 `instr` 全表扫描是下一步延迟优化的主要目标（可考虑精确词倒排或 FTS5 unicode61 通道）。

### 8.11 第十四轮：延迟剖析与批量取回（2026-11-17 追加）

八套语料里 TREC 8.7k 文档的 p50 约 360 ms，是延迟上界；project 249 文档只有 27 ms。用 `OPENFUTURE_SEARCH_PROFILE=1` 分段后：

| 阶段 | 耗时 | 说明 |
| --- | --- | --- |
| anchors | 128–137 ms | `instr(text_lower, ?)` 对 8.7k 行做字面扫描：纯扫描 55 ms + 8 个 anchor × 逐行 `instr` 约 85 ms |
| words | 50–70 ms | FTS5 porter 词干通道 |
| dense | 31–57 ms | e5 `embedQuery` + 余弦 |
| prf | 44–47 ms | 首轮 top-3 伪相关反馈 |
| merged | 86–144 ms | 候选取回 + 启发式重排 + 去重排序 |

- 改动：新增 `loadHits()` / `documentTexts()` 批量取回，把 `refs` 与重排正文从「每个候选一条 SQL」降到最多 3 条 `IN (…)`；候选集合与排序不变，五套语料分数完全一致（0.7469 / 0.6948 / 0.6992 / 0.9958 / 0.8929）。
- 负结果：`anchors` 上限 6/10/16 对 TREC 无稳定收益（p50 374/380/359 ms，query 本身只有 5–7 个词）；把 `text_lower` 拆到窄表后 anchors 只从 140 → 115 ms（读放大不是主因，`instr` 本身是）；用 `search_words` 短语查询统计 matched 只需 20–30 ms，但 porter 词干与字面子串语义不同，会改变打分，需重新调参，暂不采用。
- 结论：p50 与「语料字节数」近似线性，8.7k 医学摘要 ≈360 ms、249 篇项目文档 ≈27 ms；要再降一个量级需要为 anchors 建倒排索引（term→doc），属于 schema 级改动，留待后续。

### 8.12 第十五轮：锚点倒排可行性（2026-11-17 追加，未采用）

- 做法：在快照上建 `_anchor_eval(doc, term)`，把每个文档去掉标题行后的英文 token（≥2 字符、不含 CJK）作为 term，8.7k 文档得到 **783,611 行**；查询时 `WHERE term IN (…) GROUP BY doc ORDER BY COUNT(*) DESC LIMIT 20`。
- 收益：单次查询 **0.76 ms**，对比现在的 `instr` 全表扫描 128–137 ms，理论上能把 TREC p50 从 ~360 ms 降到 ~230 ms。
- 但语义不等价：现在 anchors 用 `instr(text_lower, anchor)`，是**子串**匹配（"covid" 命中 "covid19"、"common" 命中 "commonly"、"10" 命中 "100" 与 "10秒"）；倒排表是**词边界**匹配。同一组 anchor 的 top-20 文档集合重合只有 **2/20、8/20**，名次几乎全不同，说明候选集会被改写。
- 若采用需要重新扫 anchor 权重（0.45/0.8）与 `CANDIDATE_SCALE`，并补 CJK bigram 的子串语义（或对 CJK 回退到 `instr`，但中文语料小、本来就只要 ~30 ms）。
- 结论：本轮不改 schema。延迟目标（<500 ms）已达成，继续压低需要「倒排 + 重新调参」的整轮预算，收益 ~130 ms；优先级低于质量与稳定性，留待后续。

### 8.19 精确重排开关（2026-11-17 22:10 第二十二轮）

```
设置面板 ──memoryQualitySet(true)──▶ main/ipc ──setMemoryQualityRerank──▶ settings.json
                                     └──memoryHost.setRerank(true)──▶ memory-host 进程
                                                                          ├─ process.env.OPENFUTURE_RERANK='model'
                                                                          ├─ process.env.OPENFUTURE_RERANK_TOP='3'
                                                                          └─ await warmReranker() → { rerankerReady }
```

- `PublicSettings.memoryQualityRerank`（默认 false）经 `SettingsFile` 持久化；`memoryEnvironment()` 重启时把它翻译成 `OPENFUTURE_RERANK=model` / `OPENFUTURE_RERANK_TOP=3`，因此面板状态、环境变量、实际行为三者一致。
- `MemoryWorkspaceState.qualityRerank` 反映**开关**，`rerankerReady` 只反映模型是否已加载（关闭开关后模型仍驻留内存，面板文案以 `qualityRerank` 为准）。
- 面板总览里「精确重排 已开启 / 未开启（默认）」按钮点击即切换，1.5 s 后刷新状态；首次开启会下载并加载 280 MB 模型（约 3 s），之后的查询每次多 0.2–0.35 s。

实测（真实 8k 医学库，同一批查询）：

| 配置 | 单次检索 |
| --- | --- |
| 默认（启发式加权 RRF） | 205–229 ms |
| 精确重排（cross-encoder top3） | 423–558 ms |

质量侧（项目文档语料）：nDCG@10 0.893→0.947、R@1 0.767→0.900、MRR 0.856→0.943；短文档/英文摘要（合成语料、TREC、SciFact）反而掉分，所以默认关闭。

五套语料全量对比（`OPENFUTURE_RERANK=model OPENFUTURE_RERANK_TOP=3 OPENFUTURE_RERANK_WEIGHT=0.3`，`tools/rag-regress.mjs --tag=quality`）：

| --- | --- | --- | --- | --- | --- |
| TREC-COVID 8k | 0.7469 | 0.5083 | 339 ms | 497 ms | 掉分 |
| trec-zh（中文问英文） | 0.6948 | 0.4629 | 259 ms | 699 ms | 掉分 |
| SciFact 5.2k | 0.6992 | 0.5052 | 371 ms | 421 ms | 掉分 |

结论不变：cross-encoder 只在「同一语言 + 长文档 + 中文问答」这一档有效，其余语料上会把词面命中强的文档排后，所以默认关闭、面板开关做成持久化的 opt-in。

| 标题写两遍（body 与 title 都含标题） | boost 1 / 2 | 0.7270 / 0.7275 | 0.5724 / 0.5758 | 0.6912 | 掉分 |
| 标题只写 title、body 去掉首行 | boost 1 / 2 | 0.7347 / 0.7317 | 0.5899 / 0.5791 | 0.7020 / 0.6955 | +0.0014，噪声内，需 schema 升版，回退 |
| 缩写/同义词扩展（55 组医学映射） | 权重 0.3 / 0.6 | 0.7320 / 0.7314 | 0.5833 / 0.5833 | 0.6986 / 0.6979 | 略降，默认关 |

- 「标题只写 title」是机制上正确的做法（BM25 字段加权本应如此），但收益只有 +0.0014（R@1 +0.0033），落在单次运行的噪声里；为了 +0.14% 的 nDCG 让索引升版、重灌五个快照不划算，因此回退，记录为「可行但不经济」。
- 缩写映射（`covid-19 → sars-cov-2`、`mi → myocardial infarction` 等）只对整词生效，仍然略降：说明 SciFact 的首条误差主要来自**表述改写**而不是缩写缺失，BM25 加词反而引入噪声。
- 新增 `src/memory-host/synonyms.ts` 与 `OPENFUTURE_SYNONYM_WEIGHT`（默认 0，完全关闭，不产生查询）。保留它是为了下一轮接 LLM 改写时复用同一通道；默认关闭意味着零运行时开销。
- 结论（连续两轮一致）：SciFact 词法融合已到平台，R@1 ≈ 0.59；继续加词面信号是负收益。下一步要么换更强的英文/多语语义模型，要么引入真正的查询改写（LLM/生成模型），后者需要先解决离线评测中“没有生成模型”的问题。

### 8.26 英文特化 embedding 对照与零权重锚点短路（2026-11-18 02:05 第三十轮）

8.25 的结论把方向指向「换更强的英文语义模型」，本轮用 Xenova/gte-small（30M、384 维、CLS pooling、无前缀）做对照：复制 `.scratch/bench/scifact-e5` 为 `scifact-gte`，清空语义表，用 `OPENFUTURE_EMBED_MODEL=Xenova/gte-small` 离线重嵌 5,831 块（约 10 分钟）。

| 模型 | nDCG@10 | R@1 | R@10 | MRR | p50 |
| --- | --- | --- | --- | --- | --- |
| multilingual-e5-small（默认） | 0.7333 | 0.5866 | 0.8627 | 0.7004 | 298 ms |
| gte-small（英文特化） | 0.7354 | 0.5794 | 0.8661 | 0.6980 | 499 ms |

- nDCG/MRR 在噪声内（+0.002 / −0.002），R@1 反而低 0.7 点、R@10 高 0.3 点，延迟高约 200 ms。**英文特化模型并没有补上「表述改写」的差距**——SciFact 的平台不是 embedding 选型问题，而是 BM25/向量都无法把「同一结论的不同说法」对齐；这需要生成式改写，而不是另一个编码器。
- 因此不做「双语义通道」：现有 `semantic_vectors` 主键只有 `hash`，同时存两个模型需要 schema 迁移与双倍嵌入（8.7k 块 × 2），换来的只是噪声级收益，不做。
- 顺带修掉一处浪费：claim 查询的锚点权重是 0（实测禁用锚点 +3 nDCG），但锚点 SQL 仍会扫描 5.8k 行再以 0 权重融合。改为提前计算 `anchorWeight`，`anchorWeight === 0` 时跳过锚点查询与列表项：
  - SciFact：nDCG/R@1/MRR 与修复前**逐位相同**（0.7333 / 0.5866 / 0.7004），p50 420→298 ms（−29%）、p95 744→419 ms；
  - TREC（锚点权重 0.45）与中文（0.8）路径不变。



### 8.27 claim 的谓词停用词（2026-11-18 02:15 第三十一轮）

SciFact 的 claim 形如「X improves Y in Z」：谓词（improves/associated/patients…）在几乎每篇摘要里都出现，IDF 趋零，直觉上会稀释实体词。于是加了一组 60 余词的 claim 停用词表（仅当 `isClaimQuery` 且 `OPENFUTURE_CLAIM_STOPWORDS !== '0'` 时从 BM25 查询里剔除），实测：

| 设置 | nDCG@10 | R@1 | R@10 | MRR |
| --- | --- | --- | --- | --- |
| 基线（默认） | 0.7333 | 0.5866 | 0.8627 | 0.7004 |
| claim 谓词停用词 | 0.7292 | 0.5851 | 0.8594 | 0.6929 |

- 掉 0.4 点（R@1/MRR 同时下降）→ **已回退**，代码恢复为只用通用英文停用词。原因是 BM25 的 IDF 已经把这些高频谓词的贡献压到很低，而剔除它们会改变查询长度归一化，让剩余实体的分数分布更平；谓词本身有时也是区分信号（「reduces」vs「no effect」）。
- 该结果与 8.24–8.26 一致：claim 的瓶颈是**语义改写**，不是「查询里有噪声词」。凡是靠删词/加词的操作，都只能得到噪声级或负收益。

### 8.28 双语词表扩容与空格无关匹配（2026-11-18 02:20 第三十二轮）

trec-zh（10 条中文查询 / 8k 英文摘要）是五套语料里最弱的一档（0.6948）。逐条看，10 条里 8 条的 top1 已经正确（MRR 1.0），差距在 top10 的覆盖密度；每条都含 glossary 可覆盖的概念，但两处摩擦：

- 词表覆盖不足：mRNA 疫苗、临床证据、变异株、免疫原性等只映射到 1–2 个英文词，召回不到「同一结论的不同论文」；
- 空格不稳定：`mRNA 疫苗` / `mRNA疫苗`、`维生素 D` / `维生素D` 在中文里混用，词表按字面 `includes` 只能命中其中一种写法。

修复：新增 19 组词条（临床试验、随机对照、不良反应、变异株、奥密克戎、德尔塔、封锁、社交距离、无症状、潜伏期、重症监护、免疫原性、疫苗犹豫、再感染率、免疫持续时间等），并把匹配改为「去掉空格后比较」（`compact.includes(zh.replace(/\s+/g,''))`）。

| 设置 | nDCG@10 | R@1 | MRR | p50 |
| --- | --- | --- | --- | --- |
| 扩容前（权重 1.2） | 0.6948 | 0.0051 | 1.000 | 285 ms |
| 扩容后（权重 1.2） | **0.7004** | 0.0051 | 1.000 | 350 ms |
| 扩容后（权重 2.0） | 0.6505 | 0.0051 | 1.000 | 255 ms |

- 中文合成语料完全不变（0.9958）：英文术语在中文库里命中不到，符合「只增量、不污染」的设计。
- 权重仍是 1.2 最优：2.0 会让翻译词列表压过原生 BM25，掉 5 点。
- 结论：这类「词表 + 形态归一」在跨语言场景是稳定的小额收益（+0.56），但不可能把 0.70 推到 0.9——上限由翻译覆盖率决定。

### 8.29 真实对话查询的延迟基线（2026-11-18 02:35 第三十三轮）

前面五套语料都是**人工构造的查询**，缺了「真实用户在对话里问什么」这一维。真实库的 `retrieval_events` 表正好记录了每次 `memory_search` 的 query/hits/score/耗时，于是：

1. 从真实库导出最近 200 条检索事件，过滤测试语料（`HALCYON`、`storage-NN`、TREC 文档 id）后去重，取 40 条，落到 `.scratch/beir/live-queries.json`（实际 34 条：中英文医学问题、项目功能问题、代码标识符混合）；
2. `tools/rag-bench.mjs` 新增 `--dataset=live`：复用 8k 英文库快照（`.scratch/bench/live-e5`），只统计延迟、空结果数、top3 与 topScore，不计算 nDCG（没有 qrels），报告里 `graded:false`。

| 指标 | 值 |
| --- | --- |
| 查询数 / 空结果 | 34 / 0 |
| p50 / p95 | **261–286 ms / 438–466 ms**（两次运行） |
| topScore p10 / p50 / p90 | 0.06 / 7.3 / 31.2 |

- 空结果为 0：任何真实问句至少能返回 3 条（RRF 保底），不会出现「查不到」的空白面板。
- 延迟与 TREC 一致（261 vs 406 ms；live 里有些查询更短、锚点更少），说明评测台的数字可以外推到真实对话。
- topScore 不可跨查询比较（RRF 分数取决于命中通道数），只适合同一查询做 A/B；面板不展示它，只展示命中数与耗时。
- 这份集合也解释了产品侧现象：库是英文医学语料，中文问句靠双语词表 + e5 语义，nDCG 上限受翻译覆盖率约束（§8.28）；项目功能类问题（「记忆库切块的 token 上限」）在医学库里没有答案，返回的是分数较低的无关文档，属于预期。

### 8.30 memory_get 返回全文（2026-11-18 13:00）

真机对话暴露了一个工具层缺陷：`memory_get` 原来只返回 180 字左右的 excerpt，agent 拿到后无法回答「具体数字」类问题，只能转去 `read` 原始文件（而原始文件在 workspace 之外，被沙箱拒绝）。修复：

- `src/memory-host/index.ts` 新增 `MEMORY_GET_CHARS = 12_000` 与 `rawMemoryText(workspaceId, kind, docId)`（evidence 取 `quote`、note 取 `body`、wiki 取 `body`），`get` handler 命中后把 `hit.excerpt` 换成全文，超长时追加「…（内容过长，已截断）」。
- `src/agent-host/memory-tools.ts` 的 `memory_get` 描述改为 “Returns the full stored text of that item (up to ~12,000 characters)”，避免模型以为只能拿摘要。

效果：同一问题（延迟腹腔镜胆囊切除术）第二轮对话 23 秒、8 步完成，`memory_get` 128 ms 拿到全文，回答给出转开腹率 **11.9%→27.9%**、术后并发症 **5.7%→13%**、再手术率 **0.9%→3.0%**（P<0.001/0.007），并注明「单中心登记库观察性队列、非 RCT」。`memoryMetrics` 104 次、命中率 100%、p50 673 ms。

### 8.31 回答的 Markdown 渲染（2026-11-18 13:15）

`RichText.tsx` 原来只识别文件链接，表格/标题/列表以原始 `|`、`###` 显示。改为轻量块级解析：

- 块级：fenced code、GFM 表格（第二行匹配 `/^\s*\|?\s*:?-{2,}/`）、`#` 标题（`md-h1..6`）、引用、有序/无序列表、段落；行内：`code`、**bold**、*italic*、文件/URL 链接。
- 样式：`.md-table`（横向滚动、`white-space: nowrap`）、`.md-code`、`.md-inline-code`、`.md-list`、`.md-quote`、`.md-h`。
- 验证：真实回答里「结局 / 入院当天(d0) / 延迟至 ≥6 天 / P 值」表格渲染为四行表格，`md-table=1`、`md-h=4`、`md-list li=3`，不再出现原始管道符；截图 `.scratch/md-rag-table2.png`。

## 8.32 重排默认开启：排序 bug、模型对照与语言分流（2026-11-18）

用户要求「重排是肯定要开的」，于是把 cross-encoder 从 opt-in 改成默认开启，并重新调参。

### 先修一个排序 bug

`refs` 来自 `fused` Map 的插入序，而不是 RRF 排名序；模型重排分支只对头部排序、尾部沿用插入序。因此把权重调到接近 0 时结果仍与 `hybrid` 差 20 点（TREC w=0.001 只有 0.5157）。修复是在计算 `maxRrf` 前执行 `refs.sort((left, right) => right.score - left.score)`。修复后 w=0.1/top3 从 0.5157 回到 0.7547。

### 模型对照（TREC，纯重排 w=1/top0/全文）

| 模型 | nDCG@10 | p50 |
| --- | --- | --- |
| `Xenova/bge-reranker-base`（279 MB） | 0.5855 | 4.7 s |
| `Xenova/ms-marco-MiniLM-L-6-v2`（23 MB） | 0.5626 | 1.2 s |
| `Xenova/ms-marco-MiniLM-L-12-v2`（34 MB） | w0.15 = 0.7727 | — |

MiniLM-L-6 在融合后的排序上更好（0.7766 vs bge 的 0.7 档），而且快 4 倍，因此英文默认换 MiniLM。

### 英文语料扫描（MiniLM-L-6）

- TREC（全候选）：w0.08=0.7663、w0.10=0.7691、w0.12=0.7706、**w0.15=0.7766**、w0.20=0.7663、w0.25=0.7715、w0.30=0.7691；top3/w0.15=0.7547（头部化掉 2 点）；480 字符 w0.15=0.775、p50 约 0.44 s，全文 0.7766、p50 1.5 s。
- SciFact：480 字符 w0.15=0.7288（低于 0.7333）；**全文 w0.15=0.7363**（R@1 0.5816、MRR 0.7009），p50 1.03 s。

### 中文语料：交叉编码器全线掉点

- project：全文 w0.15=0.8032、top3 w0.3=0.7732、top5 w0.15=0.8032、top1 w0.5=0.6994，全部低于词法重排的 0.9175。
- 合成中文：全文 w0.05=0.83、w0.15=0.8884、w0.25=0.9536、top3=0.8413、top1=0.8154，全部低于 0.9958。
- 换成 563 MB 的 `Xenova/bge-reranker-large` 后合成中文 w0.15=0.9140，仍远低于词法重排。
- 结论：中文查询保持词法/启发式重排；交叉编码器只对英文生效，翻译扩展的跨语言探针同样跳过。
