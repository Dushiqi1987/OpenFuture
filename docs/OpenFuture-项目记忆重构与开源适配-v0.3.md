# OpenFuture 项目记忆重构与开源适配 · v0.3 补充设计

2026-11-09 · 适用于 Windows 桌面端 · 在 v0.2 项目壳的 A 批之后落实

本设计调整 v0.2 的项目记忆 B 批。项目创建、主题、侧栏、对话迁移与模型中心依照 v0.2。记忆能力按项目主要用途选择，共用证据、来源修订、项目授权和发布记录。当前基线以 P3.4 可运行资源和对应源码为准，本文为代码与交付记录审查，未将 P3.4 安全整改自测计作独立复验。

## 1. 当前实现与判断

| 能力 | 目前实际实现 | 差距 |
|---|---|---|
| RAG 导入 | 手动导入 UTF-8 文本和会话证据，文件上限 2 MB。按空行并段，长段按约 1,400 字符切分。定位是字符区间 | PDF、OCR、版面与表格还原、按标题和 token 切块均未接入 |
| RAG 查询 | SQLite FTS5 trigram，另有短词字面匹配。可选 QMD 对证据生成 Markdown 语料，每次查询调用 `update()` 与 `searchLex()`。搜索使用传入查询词 | 尚未调用 QMD 向量或混合接口，无独立查询改写、融合重排与证据组装策略。FTS、QMD 词法和 Wiki 返回的分数直接合并排序，分数含义不一致 |
| Wiki | 本地以单个来源为单位生成草稿，正文从该来源前几条证据摘录，支持审批和撤销。可选 pi-llm-wiki MCP 读取，P3.4 的开发记录称已接通读取及工作区绑定 | 缺按主题跨来源编译、增量更新、冲突提示、编辑差异和逐段出处。外部 vault 的逐项目桌面配置和独立详情仍待完善 |
| Dreaming | 现有 L0–L3、会话手动取证、待审、发布、回滚与 L3 注入。规则引擎按同标题合并、按时间降级，并从资料提取首段生成晋升建议 | 当前规则流程没有跨会话的离线模型整理、语义冲突裁决或分阶段作业。P3.4 安全修复需跨版本回归 |

关键定位为 `src/main/ipc.ts` 的资料导入，`src/memory-host/index.ts` 的 `chunkText`、`searchQmd`、`allowedKinds`、`searchMemory`、`generateWiki`、`dreamStart`。当前 `rag` 和 `both` 检索允许的条目类型一样，组合主要增加了专用 Wiki 工具。它没有定义先查哪个库、何时下钻、如何去重。保留 FTS5 快速查询、证据定位、项目权限和审核回滚；按以下策略重写索引与消费方式。[P3.4 交付记录](P3.4-验收整改记录.md)

## 2. 新建项目时的记忆选项

| 策略 | 用户何时选 | 默认行为 |
|---|---|---|
| **资料检索 · RAG** | 资料多、相对稳定，常问文档里的细节 | 索引选入的资料。搜索原文片段、生成有页码或路径的引用。Wiki 编译、历史整理和 L3 默认关闭 |
| **长期知识库 · Wiki** | 资料较少但需要长期维护，常更新约定、术语、设计决策 | 查已发布的主题页。必要时沿出处读原文。用户选择更新哪些页，先出草稿和 diff |
| **会话沉淀 · Dreaming** | 长期迭代，反复出现偏好、决策、纠错和任务教训 | 只整理授权会话和选入资料。先生成候选，经审核后形成 L1/L2 和少量 L3。自动任务与 L3 出站分开控制 |
| **关闭** | 临时项目，或只需要普通对话 | 保留 Pi 历史，关闭记忆采集、查询、后台整理与注入 |

删除创建页的「组合模式」大按钮。项目设置的高级区允许显式打开附加能力，并解释先后顺序。例如「Wiki 优先，证据不足时补查原文」。同一来源的 Wiki 摘要和原文命中按出处去重；要求核对原话时保留原文。旧 `both` 保留原有权限和数据并标记「旧组合策略」，用户在预览差异后迁移。每项目拥有独立索引、vault、记忆版本、权限、预算和队列。

## 3. RAG · 从文件到可验证回答

```text
用户授权导入 → 解析和清洗 → 分层切块 → 证据与来源修订
                                 ├─ 关键词索引
                                 └─ 向量索引
问题 → 原查询 + 可选改写 → 双路候选 → 排名融合 → 重排
     → 权限复核、去重和预算 → 带出处的工具结果 → Pi 回答
```

### 3.1 导入与索引

- **优先复用 Docling**。用可取消、有限资源的本地 Python worker 转换电子 PDF、扫描 PDF 和支持的文档格式，优先保留文字层、页码、阅读顺序、标题、表格及其表头。对文字层缺失或异常的页触发 OCR，保留 OCR 标志与可用置信信息，低质量页标为待核验。按 Windows 中英文夹杂扫描件验收。纯文本继续用现有轻量读入。pypdf 可以作为电子 PDF 的轻量提取路径，扫描图像仍需 OCR。禁止执行导入文档内容，失败时保留前一可用版本。[Docling](https://github.com/docling-project/docling) · [pypdf 提取说明](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)
- **按结构优先切块**。保留标题层级、段落、列表、表格和图注，超预算才递归到句子。复用 Docling 的 `HybridChunker` 做结构和 token 约束，按实际 embedding tokenizer 计数。起始目标 400–700 token，仅给跨边界内容有限重叠，按评测调优。正文引用从原文定位获取；标题路径可用于提升检索，附加元信息不冒充原文。每块记录 `projectId、sourceId、sourceRevision、chunkId、locator、contentHash`。[Docling 分块文档](https://docling-project.github.io/docling/concepts/chunking/)
- **增量建库**。按项目将可检索证据投影到 QMD。版本固定从当前已验证词法的 QMD 2.8.3 开始，用 SDK 做 `update` 和 `embed`。重复导入相同内容去重，修改时重建受影响的块，查询阶段不扫描整个语料。检索返回时回表验证当前项目、活跃源修订和块 ID；撤销即时失效，即使索引尚未更新。嵌入模型、维度、分块版本进入索引标识，切换后重建新索引并再切换。QMD 内部若再切子块，保留证据 ID 映射，能定位时引用页或子段，否则退到原块定位。
- **交付验证**。QMD 和 Docling 置于可选本地资源组件，桌面显示下载大小、来源、许可和准备状态。默认不自动拉取模型或向外部发送资料。先验证随 Windows 可运行目录使用独立 Node x64 worker、SQLite 扩展和推理运行时。词法可用而向量不可用时显示「仅关键词」，并记录明确回退原因。[QMD 固定版本文档](https://github.com/tobi/qmd/blob/v2.8.3/README.md)

### 3.2 检索、重排和上下文

1. 保留原问题中的人名、型号、参数、路径和引用号。对省略主语、跨轮指代和复杂问题增加少量可选改写，原问题继续参与召回。改写失败使用原问，改写结果只作为查询字符串。远程改写需项目授权，发送内容限于所需问题上下文。
2. 在独立 Node worker 内接入 QMD 的混合 `store.search`，以 SDK 实际签名为准。优先复用其词法与向量召回、基于名次的 RRF 及 reranker。中英混合语料对照 QMD 默认 embedding 与其文档列出的 Qwen3-Embedding；以实测选型。若内置链路在 Windows 无法部署，才验证替代路径，例如 LanceDB 的全文、向量、RRF 加可选 reranker。两套引擎同一次交付选一个主路径，避免重复建索引。[QMD 混合检索](https://github.com/tobi/qmd/blob/v2.8.3/README.md) · [LanceDB 混合检索](https://docs.lancedb.com/search/hybrid-search)
3. 分清候选 `K`、重排后片段数 `N` 和最终 token 预算。首轮从约 30 个融合候选、4–6 个最终片段做实验。剔除重复、低相关和失效片段，必要时合并相邻块或补齐不同来源。对不同来源与算法的分数，使用共同排名或明确的路由规则。最终片段数可随相关性和预算减少。
4. 实现两种证据排布实验。A 为重排降序，B 为两端优先，三个片段时用 `#1 → #3 → #2`。证据排布只改变证据块内顺序。固定系统规则和当前真实问题的位置，保留 ID、标题、页码、日期和原文片段。对照模型、上下文长短和单跳／多跳题；仅在配对评测受益时启用 B。现有研究观察到长上下文中的位置效应，也表明检索质量与模型选择会影响结果。[Lost in the Middle](https://arxiv.org/abs/2307.03172) · [RAG 位置效应复现](https://arxiv.org/abs/2605.27105)
5. 给工具结果附可核验的来源修订与内容身份，保留当轮有效结果。撤销、替换或切换项目后，过滤失效结果及其派生内容。面板区分「查到了什么」和「模型这次收到什么」。空结果或来源不足时明确展示，模型给出证据不足的回应。

## 4. Wiki · 从摘录草稿到可维护主题库

- 复用本机已安装并验证过 MCP 入口的 `pi-llm-wiki 0.12.5`。按项目在暂存 vault 执行 bootstrap、capture、ingest、lint、recall；开发先用固定版本的 `tools/list` 确认实际工具契约和后台模型要求。暂存 vault 只接收该项目授权的文件副本与必要配置；如果 ingest 依赖外部模型，连接必须由用户选择并显示将发送什么。[pi-llm-wiki 上游仓库](https://github.com/zosmaai/pi-llm-wiki)
- 以主题为主键生成或更新页，支持多来源归并、相关主题链接、矛盾并列、逐段证据引用和更新时间。显示现有页与新草稿 diff，可编辑和审核；按当前版本和有效来源核验后发布。同一来源修订只触发受影响主题，未审核草稿不被 Agent 查到。
- 普通对话先查当前项目已发布主题，再读取正文和必要出处。少量文档用 Wiki 自己的目录、标题和全文检索即可。撤销来源后，对受影响段落重新计算、隐藏或提示待复核；有效段落继续可读。始终按项目校验 vault 绑定和稳定页 ID。

## 5. Dreaming · 对齐 Claude 公开行为

Anthropic 公开描述了会话记录、笔记、可查询的表示层及注入上下文。其 Dreams 读取既有记忆和历史会话，输出独立的新记忆库。OpenFuture 以这组公开行为为目标，沿用用户参考方案的五阶段作为本项目任务协议。这里的「离线整理」指从实时问答链路移出；只有显式选用本地模型时才保证断网可整理。[Anthropic 记忆架构说明](https://www.anthropic.com/research/components-of-agent-memory) · [Claude Dreams 文档](https://platform.claude.com/docs/en/managed-agents/dreams)

| 阶段 | 输入与产物 |
|---|---|
| Ingest | 读取项目授权且已完成的 Pi 会话分支和资料。保留原记录，增量记录消息 ID、说话人和来源。排除推理块、旧注入、重复工具结果和已撤销数据 |
| Light | 提取带证据的偏好、项目决策、纠错和开放问题，写入暂存候选。区分用户确认、工具结果、模型陈述 |
| REM | 跨会话聚类和归并，维护主题、时间与反例。可选更新项目 Wiki 草稿，对冲突保留双方出处 |
| Deep | 生成结构化 keep/fix/merge/drop/promote 等裁决，核验项目、真实证据 ID、来源和目标修订。模型提出建议，发布器与用户决定是否采纳 |
| Promote | 展示版本 diff 和 L3 预览。用户确认后创建新版本及审计记录，原子切换活跃版本。L3 优先保留稳定且反复有用的已批准条目，满足行数、字节和模型 token 三重预算 |
| Verify | 发布前验证引用、删除比例、重复和注入预算。发布后复验问题回答、引用、撤销和回滚。支持任务失败后从安全检查点重试 |

后台调度默认关。开启后只为已授权项目整理，限制并发、成本和任务次数，展示阶段、失败原因及待审结果。每轮调用前重新校验项目策略和证据状态。严禁把文档文字或模型的旧回答当作可信指令或事实。回滚保持当前撤销状态。只有批准后生成的有效 L3 才允许出站。

## 6. 交付拆分与验收门槛

| 批次 | 可交付验收 |
|---|---|
| B0 · 策略与隔离 | 项目 A 选择 RAG，项目 B 选择 Wiki，项目 C 选择 Dreaming。每项目独立绑定资源与权限。切换、重启、旧 ID、待审候选、来源撤销以及 P3.4 的 OF-01 至 OF-05 全部按隔离环境复测 |
| B1 · RAG | 固定合成或授权的电子 PDF、扫描 PDF、中英文混合、跨页表格、型号与多跳问题。先跑现有词法基线，再跑结构切块和混合重排。记录 Recall@K、nDCG@N、回答正确率、引用页码正确率、延迟及索引体积。报告排序 A/B 结果。验证无模型、断网、删除、替换、重启和旧索引误命中 |
| B2 · Wiki | 三份资料形成一个带逐段出处的主题。新增、替换、撤销单个来源，验证只更新受影响主题，发布前后能看到 diff，跨项目无内容泄露 |
| B3 · Dreaming | 两段已授权会话提供冲突偏好，第三段未授权会话含哨兵。暂存只看授权内容并提出有证据的纠正，批准前旧版本可用，批准后新请求使用新版本，撤销和回滚后不会复活已失效事实。校验中断、重复发布、成本预算和拒绝假证据 |

每批保存独立 Windows EXE 目录、资源哈希、实际出站验证和未通过项。保留旧数据与既有候选，继续用测试目录和合成数据。依赖需记录固定版本与许可。代码许可与 OCR、embedding、reranker 和生成模型权重许可分开登记。Docling 和 QMD 的重型依赖以及真实模型能力先通过隔离原型，再并入默认流程。
