# 并发对话（多会话）验收记录

日期：2026-11-15。目标：让多个对话同时运行——在 A 对话生成时切到 B 发起新任务，A 继续在后台跑；切回 A 时能看到它已完成的内容。

## 1. 方案

| 选项 | 做法 | 结论 |
| --- | --- | --- |
| A | 把 `src/agent-host/index.ts` 从单会话改成按 `sessionId` 的会话表 | 需要改动 Pi 会话、工具注册表、队列、ask/subagent/group 运行时的全部单例状态，回归面大 |
| B（采用） | 每个对话一个 `AgentHost`（utilityProcess），主进程用 `HostRegistry` 管理 | agent-host 保持「一个进程一个完整会话」，天然隔离，崩溃互不影响，改动集中在主进程路由 |

- 上限：`Math.max(2, Number(process.env.OPENFUTURE_MAX_CONVERSATIONS ?? 3) || 3)`，默认 3 个同时运行的对话。
- 达到上限时先关闭空闲 host；全部在 streaming 则拒绝打开新对话（`最多同时运行 N 个对话，请先停止一个再打开新的对话`）。
- 切回已在运行的对话不重启进程：`HostRegistry.open()` 调 `host.history()` 取回会话文件与消息，渲染层直接回放。
- 仍会全局生效的操作保持重启语义：切换项目/工作区、切换记忆模式、保存模型设置 → `closeAll()` / `restart()`。

## 2. 改动位置

| 文件 | 内容 |
| --- | --- |
| `src/main/host-registry.ts`（新） | `HostRegistry`：`hosts`、`spareHost`、`open/require/send/stop/close/closeAll/restart/reloadPlugins/list/adaptPlugin/answerPrompt/startGroupChat`，空闲驱逐与上限校验 |
| `src/main/index.ts` | `agentHost` 改为 `HostRegistry`；自动化投递按 `sessionId` 路由 |
| `src/main/ipc.ts` | 打开/发送/停止/关闭/作答/群聊全部按 `sessionId` 路由；切项目、切工作区才 `closeAll()` |
| `src/main/agent-host.ts` | `history()`、`isStreaming()`、`hasSession()`；`send/stop` 接受 `sessionId` |
| `src/agent-host/index.ts` | 新增 `history` RPC（返回 `sessionFile` 与回放消息） |
| `src/shared/protocol.ts` / `src/preload/index.ts` | `sendMessage(text, mode?, sessionId?)`、`stop(sessionId?)`、`closeSession(sessionId?)`、`answerPrompt({sessionId})`、`startGroupChat({sessionId})` |
| `src/renderer/src/App.tsx` | `runningSessions` 集合、跨会话事件跟踪、切走不再拦截、后台圆点、消息回放 |
| `src/renderer/src/styles.css` | `.conversation-live` 运行中圆点（`chain-pulse` 动画） |

## 3. 验证

```bash
node_modules/.bin/electron-vite build   # 或 pnpm build
node tools/e2e-multi.mjs
```

E2E（慢速 mock，`MOCK_DELAY_MS=90`）实际输出：

```
mock model ready
model saved
conversation A streaming -> 01a1daef-4fb1-73b8-b0d0-0f48fa1c99f5
settled sessions -> ["01a1daef-4fb1-73b8-b0d0-0f48fa1c99f5","01a1daef-5b80-76d0-a277-de6a1da410c3"]
host starts -> 2
replay -> {"hasPrompt":true,"hasAnswer":true,"active":"对话 A"}
E2E PASSED
```

断言内容：A 在 streaming 时切到 B 并成功开跑；两个不同 `sessionId` 各自 `settled`；主进程日志出现两条 `[agent-host] started`（每个对话一个 host）；切回 A 能看到「第一段」提问与完整回答。

截图：`.scratch/e2e-multi.png` → `docs/assets/multi-conversation.png`。

## 4. 已知限制

- 后台对话完成后侧边栏不会自动重排（`updatedAt` 刷新要等下次打开列表），只有运行中显示圆点。
- 同一对话重复发送仍走原来的 steer/followUp 队列语义，不会并行跑两个回合。
- 关闭对话只释放该 host；切换项目/工作区仍会关闭全部 host（环境级变更）。
- 每个 host 都是一个 utilityProcess，3 个对话约增加 3 份 Pi 运行时内存；内存紧张时可把 `OPENFUTURE_MAX_CONVERSATIONS` 调到 2。

## 5. 复现环境

- Windows 11、Node v24.21.0、Electron 45.2.3、Pi 1.5.0。
- 离线：`tools/mock-model/server.mjs`（`MOCK_DELAY_MS=90`）。
- 测试脚本自带 userData 与工作区隔离（`.scratch/e2e-multi-*`），不会污染真实配置。
